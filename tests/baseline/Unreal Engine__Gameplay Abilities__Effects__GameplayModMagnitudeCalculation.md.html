GameplayModMagnitudeCalculation

Overview

An MMC is a class that computes the magnitude of a single gameplay effect modifier using custom logic. Instead of using a fixed number, ScalableFloat, or AttributeBased float, you write C++ or Blueprint code that runs every time the effect applies, giving you full control over the math while staying inside a single modifier slot. The engine calls your calculation, then feeds the result through the standard modifier pipeline — coefficient, pre-add, post-add, curve lookup — and applies it to the target attribute. > [!info] Source > Engine/Plugins/Runtime/GameplayAbilities/Source/GameplayAbilities/Public/GameplayModMagnitudeCalculation.h

Class Hierarchy

`` UObject └── UGameplayEffectCalculation (GameplayEffectCalculation.h) └── UGameplayModMagnitudeCalculation (THIS CLASS) ` The base class UGameplayEffectCalculation` provides one thing — a place to declare which attributes you want captured:

## The Core Function — `CalculateBaseMagnitude`

```cpp
// GameplayModMagnitudeCalculation.h:30

UFUNCTION(BlueprintNativeEvent, Category="Calculation")
UE_API float CalculateBaseMagnitude(const FGameplayEffectSpec& Spec) const;
```

This is the only function you **must** override. It receives the full `FGameplayEffectSpec` and returns a float — your computed magnitude.

In C++ you override the `_Implementation` version:
```cpp
virtual float CalculateBaseMagnitude_Implementation(const FGameplayEffectSpec& Spec) const override;
```

In Blueprint you override the `CalculateBaseMagnitude` event node.

**What you get access to from the `FGameplayEffectSpec`:**

  • All captured attributes (via helper functions)


  • SetByCaller magnitudes


  • Source and Target tags


  • Effect level (`Spec.GetLevel()`)


  • Effect context (instigator, causer actors)


  • Duration, period, stack count


**What you return** — a single float. That float is the "base magnitude" that the modifier pipeline then processes further (see The Pipeline section).

## Attribute Capture System

### FGameplayEffectAttributeCaptureDefinition

Each capture definition tells the GAS system: *"capture this attribute from this source, either snapshotted or live."*

```cpp
struct FGameplayEffectAttributeCaptureDefinition
{
 FProperty* AttributeToCapture;        // Which attribute property

 EGameplayEffectAttributeCaptureSource AttributeSource;   // Source or Target

 bool bSnapshot;                       // Snapshot at spec creation, or live at execution?

};
```

### Three Fields

| Field                | Options                                         | Meaning                                                     |
| -------------------- | ----------------------------------------------- | ----------------------------------------------------------- |
| `AttributeToCapture` | `UMyAttributeSet::GetAttributeNameAttribute()`  | The specific attribute property to capture                  |
| `AttributeSource`    | `EGameplayEffectAttributeCaptureSource::Source` | Read from the ASC that *applied* the effect                 |
| `AttributeSource`    | `EGameplayEffectAttributeCaptureSource::Target` | Read from the ASC the effect is *applied to*                |
| `bSnapshot`          | `true`                                          | Value captured when GE spec is *created* (locked in)        |
| `bSnapshot`          | `false`                                         | Value captured when GE *executes* (live, up-to-date)        |

For the full capture system — how definitions become specs, how `FindCaptureSpecByDefinition` works, and the source vs target timing — see [[Core Mechanics/Attribute Capture System]].

### Snapshot vs Live — When to Use Each

| Scenario | bSnapshot | Why |
|---|---|---|
| Melee damage on hit | `false` (live) | Use current defense value at moment of impact |
| Projectile damage | `true` (snapshot) | Remember the attacker's stats when the projectile was fired, even if they buff between launch and hit |
| DOT periodic tick | `false` (live) | Each tick reads the current state — might change over time |
| Buff that counts initial stat | `true` (snapshot) | "Grant 50% of current Strength" — fix the Strength value at cast time |
| Posture damage | `false` (live) | Posture changes as damage accumulates, want current value |

### Registering Captures

You must add every capture definition to `RelevantAttributesToCapture` in your constructor. If you read an attribute in `CalculateBaseMagnitude` but didn't register it, `GetCapturedAttributeMagnitude` returns `false` and logs an error.

**Manual method (cleaner):**
```cpp
UMyMMC::UMyMMC()
{
 StrengthDef.AttributeToCapture = UMyAttributeSet::GetStrengthAttribute();
 StrengthDef.AttributeSource = EGameplayEffectAttributeCaptureSource::Source;
 StrengthDef.bSnapshot = false;
 RelevantAttributesToCapture.Add(StrengthDef);

 DefenseDef.AttributeToCapture = UMyAttributeSet::GetDefenseAttribute();
 DefenseDef.AttributeSource = EGameplayEffectAttributeCaptureSource::Target;
 DefenseDef.bSnapshot = false;
 RelevantAttributesToCapture.Add(DefenseDef);
}
```

**Macro method (common in engine examples):**
```cpp
// Header

DECLARE_ATTRIBUTE_CAPTUREDEF(Strength);
DECLARE_ATTRIBUTE_CAPTUREDEF(Defense);

// Constructor

DEFINE_ATTRIBUTE_CAPTUREDEF(UMyAttributeSet, Strength, Source, false);
DEFINE_ATTRIBUTE_CAPTUREDEF(UMyAttributeSet, Defense, Target, false);
```

The macros expand (from `GameplayEffectExecutionCalculation.h:320-337`):
```cpp
#define DECLARE_ATTRIBUTE_CAPTUREDEF(P) \

 FProperty* P##Property; \
 FGameplayEffectAttributeCaptureDefinition P##Def;

#define DEFINE_ATTRIBUTE_CAPTUREDEF(S, P, T, B) \

{ \
 P##Property = FindFieldChecked<FProperty>(S::StaticClass(), GET_MEMBER_NAME_CHECKED(S, P)); \
 P##Def = FGameplayEffectAttributeCaptureDefinition(P##Property, \
     EGameplayEffectAttributeCaptureSource::T, B); \
}
```

The macro also stores the `FProperty*` (e.g. `StrengthProperty`) — useful if you later upgrade to an ExecutionCalculation where you need the property handle to emit output modifiers.

## The Pipeline — What Happens to Your Return Value

From `GameplayEffect.cpp:1143` — `FCustomCalculationBasedFloat::CalculateMagnitude`:

```cpp
// GameplayEffect.cpp:1143-1160

float FCustomCalculationBasedFloat::CalculateMagnitude(const FGameplayEffectSpec& InRelevantSpec) const
{
 const UGameplayModMagnitudeCalculation* CalcCDO = 
     CalculationClassMagnitude->GetDefaultObject<UGameplayModMagnitudeCalculation>();
 check(CalcCDO);

 // 1. Your function runs — this is what comes back

 float CustomBaseValue = CalcCDO->CalculateBaseMagnitude(InRelevantSpec);

 const float SpecLvl = InRelevantSpec.GetLevel();
 FString ContextString = ...;

 // 2. Pipeline applies: Coeff * (YourValue + PreAdd) + PostAdd

 float FinalValue = ((Coefficient.GetValueAtLevel(SpecLvl, &ContextString) 
     * (CustomBaseValue + PreMultiplyAdditiveValue.GetValueAtLevel(SpecLvl, &ContextString))) 
     + PostMultiplyAdditiveValue.GetValueAtLevel(SpecLvl, &ContextString));

 // 3. Optional curve table lookup on the final result

 if (FinalLookupCurve.IsValid(ContextString))
 {
     FinalValue = FinalLookupCurve.Eval(FinalValue, ContextString);
 }

 return FinalValue;  // This is what actually modifies the target attribute

}
```

### The Fields in the GE Asset

All of these are `FScalableFloat` (supports curve table scaling by level):

| Field | Formula Role | Default | Use Case |
|---|---|---|---|
| **Coefficient** | `Coeff * (YourValue + PreAdd)` | 1.0 | Global multiplier — let designers tune damage |
| **PreMultiplyAdditiveValue** | Added to your value *before* coeff | 0.0 | Flat bonus that scales with the formula |
| **PostMultiplyAdditiveValue** | Added *after* coeff multiplication | 0.0 | Flat bonus that bypasses scaling |
| **FinalLookupCurve** | Curve table mapping final value → output | None | Soft-cap, hard-cap, or non-linear mapping |

**Designer-friendly:** You write the complex math in C++, designers tune with Coefficient/PostMultiply in the data asset.

**Example:** Your MMC returns `BaseDamage * StrengthMultiplier`. The designer can set `Coefficient = 0.5` in a "Easy Mode" GE and `Coefficient = 1.2` in a "Hard Mode" GE — same MMC, different tuning.

## When Does the MMC Actually Run?

Your `CalculateBaseMagnitude` is called every time `FGameplayEffectSpec::CalculateModifierMagnitudes()` runs. The key question is *when* that happens, and it depends on the effect's duration policy.

### `CalculateModifierMagnitudes()` — the call sites

| Call site (line) | When it fires | Effect types affected |
|---|---|---|
| `GameplayEffect.cpp:4388` | During **initial GE application**, before the effect becomes active | ALL types |
| `GameplayEffect.cpp:3229` | **ExecuteActiveEffectsFrom** — the instant/periodic execution path | Instant, Periodic |
| `GameplayEffect.cpp:4784` | **On each periodic tick** — re-execution of the periodic effect | Duration+Periodic, Instant+Periodic |
| `GameplayEffect.cpp:3870` | When **SetByCaller** values are updated on an active GE | Duration, Infinite, Periodic |
| `GameplayEffect.cpp:3883` | When **SetByCaller** values are updated via tag map | Duration, Infinite, Periodic |
| `GameplayEffect.cpp:3898` | When the effect's **level changes** via `SetActiveGameplayEffectLevel` | Duration, Infinite, Periodic |

### What this means per effect type

| Duration Policy | MMC runs at application? | MMC re-runs later? | Details |
|---|---|---|---|
| **Instant** | ✅ Once | ❌ No | MMC runs during application + execution (same frame), effect is gone. The modifier is applied immediately. |
| **Duration** (no periodic) | ✅ Once | ❌ No | MMC runs at application, magnitude is stored in `ModSpec.EvaluatedMagnitude`, that value persists in the FAggregator for the full duration. MMC doesn't re-run unless you manually call `CalculateModifierMagnitudes` or change a SetByCaller. |
| **Duration + Periodic** | ✅ Once at start | ✅ **Every tick** | MMC runs at application for the initial modifier, then **re-runs on each periodic tick** (`ExecuteActiveEffectsFrom` → `CalculateModifierMagnitudes()`). Each tick evaluates fresh live captured attributes. |
| **Instant + Periodic** | ✅ Once at start | ✅ **Every tick** | Same as above — periodic ticks recalculate each time. |
| **Infinite** | ✅ Once | ❌ No | Same behavior as Duration. Magnitude is frozen at application time. |

### Practical consequences

**For Duration/Infinite effects**, your MMC runs exactly once — at the moment the effect is applied. The magnitude value is locked in. If the target's stats change mid-effect, the modifier value stays the same. This is intentional — it's a "snapshot of the formula at cast time" behavior.

If you need a Duration/Infinite effect to **recalculate its magnitude while active**, you have two options:

  1. **Make it periodic** — add a period (even a long one like every 1.0s). The MMC re-runs each tick, letting you recalculate with fresh captured values.


  1. **Use `GetExternalModifierDependencyMulticast`** — return a delegate that fires when external conditions change. When it fires, GAS recalculates the modifier magnitude and updates the FAggregator. This is the efficient option (only recalculates when needed, not on a timer).


**For periodic effects**, the MMC re-runs every tick. Each tick gets fresh captured attribute values, current tags, etc. This is where `bSnapshot` vs `bLive` matters most — if you snapshot, the captured values are still from the initial spec creation, not the current tick.

**For Instant effects**, the MMC runs, the modifier is applied, the effect is removed. Single-shot.

### What about `bSnapshot` in context?

| Duration Policy | With `bSnapshot=true` | With `bSnapshot=false` |
|---|---|---|
| Instant | Same frame, no difference | Same frame, no difference |
| Duration | Captured at spec creation | Captured at spec creation (MMC only runs once, so same thing) |
| Duration + Periodic | **Captured at spec creation** — every tick uses the stale snapshot | **Captured live each tick** — recalculated every period |
| Infinite | Captured at spec creation | Captured at spec creation (MMC only runs once) |

**Key insight:** For non-periodic Duration/Infinite effects, `bSnapshot` has no effect because the MMC only runs once — at application time — and that's the same time the snapshot is taken. Snapshot vs live only matters for periodic effects where the MMC runs multiple times and needs fresh data.

## Do the Macros Do the Same Thing?

Yes — they expand to identical code. The macros are just shorthand.

```cpp
// Header: DECLARE_ATTRIBUTE_CAPTUREDEF(Strength)

// Expands to:

FProperty* StrengthProperty;
FGameplayEffectAttributeCaptureDefinition StrengthDef;

// Constructor: DEFINE_ATTRIBUTE_CAPTUREDEF(UMyAttributeSet, Strength, Source, false)

// Expands to:

{
 StrengthProperty = FindFieldChecked<FProperty>(
     UMyAttributeSet::StaticClass(),
     GET_MEMBER_NAME_CHECKED(UMyAttributeSet, Strength));
 StrengthDef = FGameplayEffectAttributeCaptureDefinition(
     StrengthProperty,
     EGameplayEffectAttributeCaptureSource::Source,
     false);  // bSnapshot

}
```

[!info] Source
`GameplayEffectExecutionCalculation.h:328-332`

```cpp
#define DEFINE_ATTRIBUTE_CAPTUREDEF(S, P, T, B) \

{ \
 P##Property = FindFieldChecked<FProperty>(S::StaticClass(), GET_MEMBER_NAME_CHECKED(S, P)); \
 P##Def = FGameplayEffectAttributeCaptureDefinition(P##Property, EGameplayEffectAttributeCaptureSource::T, B); \
}
```

**One important detail:** The macro creates the `CaptureDefinition` but does **NOT** add it to `RelevantAttributesToCapture`. You must still do:
```cpp
RelevantAttributesToCapture.Add(StrengthDef);
```

Both methods produce the same result. The only practical difference is that the macro also stores the `FProperty*` (e.g. `StrengthProperty`), which you can use if you later upgrade to a `GameplayEffectExecutionCalculation` where you need the raw property handle for `FGameplayModifierEvaluatedData` output. With the manual method you'd need to store your own `FProperty*` variable separately.

[!warning] The macro's `P` parameter is NOT a custom alias
`DEFINE_ATTRIBUTE_CAPTUREDEF(UBaseAttributeSet, Posture, Target, false)` — the second parameter `Posture` is used as **both** the variable name suffix **and** the actual attribute property lookup (`GET_MEMBER_NAME_CHECKED`). It must match the exact property name in your AttributeSet class.

If the attribute is called `Posture` in the set, you write `Posture`. If it's called `PostureDamage`, you write `PostureDamage`. You cannot invent a custom nickname — the compiler will reject it because the property doesn't exist in the class.

With the manual method there's no such constraint — your `CaptureDefinition` variable can be named anything.

## Evaluation Parameters — FAggregatorEvaluateParameters

When you call `GetCapturedAttributeMagnitude`, you pass an `FAggregatorEvaluateParameters` struct. This controls *which* of the attribute's modifiers count when computing its current value.

```cpp
// GameplayEffectAggregator.h

struct FAggregatorEvaluateParameters
{
 const FGameplayTagContainer* SourceTags;      // Your current source tags

 const FGameplayTagContainer* TargetTags;      // Your current target tags

 TArray<FActiveGameplayEffectHandle> IgnoreHandles;  // Specific GE mods to skip

 FGameplayTagContainer AppliedSourceTagFilter;  // Extra filter: only mods with source tags matching ALL

 FGameplayTagContainer AppliedTargetTagFilter;  // Extra filter: only mods with target tags matching ALL

 bool IncludePredictiveMods;                    // Include client-predicted mods?

};
```

### How Attributes Are Actually Stored

Every attribute in GAS has an internal **FAggregator** that tracks every modifier from every active GE affecting it. Each modifier has optional **tag requirements** set in the GE:

```
Attribute: "Strength"
├── Modifier: +50 from GE_BattleCry (Requires: source has "State.Raging")
├── Modifier: -20 from GE_Weaken  (Requires: target has "State.Cursed")
├── Modifier: +10 from GE_RingOfPower (No tag requirements — always applies)
└── Modifier: +30 from GE_BaseStats (No tag requirements — always applies)
```

When you ask "what is the current Strength value?", the FAggregator evaluates all modifiers... but it needs to know: **what tags does the source have right now?** And **what tags does the target have right now?**

### What SourceTags and TargetTags Actually Do

The `SourceTags` and `TargetTags` you pass are matched against each modifier's tag requirements:

```
You pass: SourceTags = [State.Raging]

GE_BattleCry modifier checks:
"Does the source have my required tags?" → Yes (State.Raging matches) → INCLUDED (+50)

GE_Weaken modifier checks:
"Does the target have my required tags?" → Depends on what you passed as TargetTags → ?
```

  • **If SourceTags/TargetTags are nullptr** (or empty containers): **No tag filtering happens.** All modifiers are evaluated regardless of their requirements. The attribute returns the raw sum of everything.


  • **If SourceTags/TargetTags contain your current tags**: Only modifiers whose requirements are satisfied by those tags are counted. Modifiers whose requirements aren't met are excluded.


### Concrete Example

You have two GEs active on your character:

| GE | Modifier | SourceTagRequirements | TargetTagRequirements |
|---|---|---|---|
| GE_Berserk | +50 Strength | Source has `State.Berserk` | None |
| GE_DefaultStats | +20 Strength | None | None |

**Scenario A — you set SourceTags correctly:**
```cpp
EvalParams.SourceTags = Spec.CapturedSourceTags.GetAggregatedTags();  // contains "State.Berserk"

```
Result: `Strength = 70` (both mods count — Berserk's requirement is met)

**Scenario B — you pass nullptr or empty SourceTags:**
```cpp
EvalParams.SourceTags = nullptr;
```
Result: `Strength = 20` (Berserk is excluded — its requirement wasn't satisfied). Wait — **actually this is wrong.** When SourceTags is `nullptr`, the aggregator does NOT filter by tag requirements at all. So:

Actually, the behavior is:

  • **nullptr/empty SourceTags → no tag filtering → ALL mods counted**


  • **SourceTags with specific tags → only mods whose requirements are a subset are counted**


So scenario B would give `Strength = 70` because without tag filtering, everything counts. This is why it's dangerous: if you forget to set the tags, you might overcount.

**To be exact**, the tag check works like this:
```cpp
// Pseudocode of what the aggregator does internally
bool ModifierShouldCount(const FAggregatorMod& Mod, const FAggregatorEvaluateParameters& Params)
{
 // If the GE has TagRequirements and we have explicit tags to check against
 if (Mod.SourceTagReqs.IsSet() && Params.SourceTags != nullptr)
 {
     // Only include if our source tags satisfy the mod's requirements
     if (!Params.SourceTags->HasAll(Mod.SourceTagReqs.GetValue()))
         return false;  // Exclude this mod

 }
 if (Mod.TargetTagReqs.IsSet() && Params.TargetTags != nullptr)
 {
     if (!Params.TargetTags->HasAll(Mod.TargetTagReqs.GetValue()))
         return false;
 }
 return true;  // Include this mod

}
```

Key rule: **If there are tag requirements AND you set a non-null tag container, the check runs. If you pass nullptr, the check is skipped entirely and the mod counts regardless.**

### What `GetAggregatedTags()` Returns

```cpp
Spec.CapturedSourceTags.GetAggregatedTags()
```

This returns a **`const FGameplayTagContainer*`** (pointer, can be null) that is the union of:

| Source | Example |
|---|---|
| **Actor Tags** on the source's ASC owner (`AActor::Tags`) | `Character.Player`, `Faction.Heroes` |
| **Spec Tags** set on the current GE spec | `Effect.AppliedByBerserk` |
| **ASC Owned Tags** on the source's AbilitySystemComponent | `State.Alive`, `Combat.InCombat` |
| **Ability Tags** from the ability that applied the GE | `Ability.Slot1` |
| **GameplayCue Tags** currently active | `Cue.FireAura` |

It's called "aggregated" because it collects tags from ALL sources — not just one.

Similarly for the target:
```cpp
Spec.CapturedTargetTags.GetAggregatedTags()
```

### How to Set It Up

```cpp
FAggregatorEvaluateParameters EvalParams;

// Always set these — they're the context for the current GE execution
EvalParams.SourceTags = Spec.CapturedSourceTags.GetAggregatedTags();  // tags of the instigator

EvalParams.TargetTags = Spec.CapturedTargetTags.GetAggregatedTags();  // tags of the target

```

### AppliedSourceTagFilter vs SourceTags — What's the Difference?

This is a common point of confusion.

| Field | What it filters | How |
|---|---|---|
| **SourceTags** | The modifier's **SourceTagRequirements** | "Does the source have the tags this mod needs?" |
| **AppliedSourceTagFilter** | The modifier's **owner GE's source tags** | "Does this mod's GE have the tags I'm looking for?" |

`SourceTags` answers: "does the current context satisfy this mod's requirements?"

`AppliedSourceTagFilter` answers: "among all mods, only look at ones whose GE has specific source tags."

Example:
```cpp
EvalParams.AppliedSourceTagFilter.AddTag(FGameplayTag::RequestGameplayTag("Effect.Type.Buff"));
```

This says: "Only count modifiers that come from GEs that have the `Effect.Type.Buff` tag on their source." All other mods (from debuffs, passives, etc.) are ignored, regardless of whether their tag requirements are met.

Use `AppliedSourceTagFilter` when you want to evaluate "what would my Strength be if only buffs counted?" — useful for tooltips, UI displays, or calculations that need a partial view.

  • **Aggregated tags** — union of both, plus anything added by the ASC or ability

## External Dependencies & Networking

### Prediction Behavior

MMCs run on **both** the client and server when the GE is predicted (applied with a valid prediction key from a predicted ability). Your `CalculateBaseMagnitude` executes on the client to compute the modifier magnitude immediately — no server round trip needed.

For the full prediction system — including `HasAuthority` vs `HasAuthorityOrPredictionKey`, the `bTreatAsInfiniteDuration` mechanism for instant effects, reconciliation, and how each GE type behaves — see [[Prediction & Networking]].

### GetExternalModifierDependencyMulticast

```cpp
virtual FOnExternalGameplayModifierDependencyChange* GetExternalModifierDependencyMulticast(
 const FGameplayEffectSpec& Spec, UWorld* World) const;
```

If your MMC depends on something outside the ability system (a game state variable, a buff on another actor, a world condition), override this to return a delegate. When that delegate fires, the GAS system recalculates the effect's magnitude automatically.

**Return `nullptr` (default)** if you have no external dependencies.

### bAllowNonNetAuthorityDependencyRegistration

```cpp
UPROPERTY(EditDefaultsOnly, Category=ExternalDependencies, AdvancedDisplay)
bool bAllowNonNetAuthorityDependencyRegistration;

/** Accessor — validates that bAllowNonNetAuthorityDependencyRegistration is compatible with attribute captures */
UE_API bool ShouldAllowNonNetAuthorityDependencyRegistration() const;
```

[!warning] Advanced Networking
From the source comment: "This is an advanced use case that should only be enabled under very specific circumstances."

**What it does:** Allows clients (non-authoritative) to register and respond to the external dependency delegate. This lets clients update MMC-based attributes without causing a network dormancy flush.

**Requirements:**

  • Your game **must** be using network dormancy (otherwise this does nothing useful)


  • Your MMC **must NOT** use attribute capture (`RelevantAttributesToCapture.Num() == 0`) — the engine asserts/ensures this


  • The external delegate must come from something guaranteed to exist on the client (not a GameState, which has timing issues)


**Default:** `false` — leave it alone unless you know you need it.

## Blueprint Usage

You can create an MMC entirely in Blueprint:

  1. Create a Blueprint class derived from `GameplayModMagnitudeCalculation`


  1. Set **Relevant Attributes to Capture** in the Class Defaults (array of capture definitions)


  1. Override **Calculate Base Magnitude** — an event node that receives `EffectSpec`


  1. Use **Get Captured Attribute Magnitude** to read attributes


  1. Return the computed float


  1. In your GE, set Magnitude → **Custom Calculation Class** → pick your Blueprint


**Blueprint limitations:**

  • Cannot use `DECLARE_ATTRIBUTE_CAPTUREDEF` macros (C++ only)


  • Tag container filters in `FAggregatorEvaluateParameters` are harder to customize


  • No access to the `GetExternalModifierDependencyMulticast` override (must be C++)

```cpp
float UPostureDamageMMC::CalculateBaseMagnitude_Implementation(const FGameplayEffectSpec& Spec) const
{
 FAggregatorEvaluateParameters EvalParams;
 EvalParams.SourceTags = Spec.CapturedSourceTags.GetAggregatedTags();
 EvalParams.TargetTags = Spec.CapturedTargetTags.GetAggregatedTags();

 float CurrentPosture = 0.f;
 GetCapturedAttributeMagnitude(CurrentPostureDef, Spec, EvalParams, CurrentPosture);

 float MaxPosture = 0.f;
 GetCapturedAttributeMagnitude(MaxPostureDef, Spec, EvalParams, MaxPosture);

 float IncomingDamage = 0.f;
 GetCapturedAttributeMagnitude(IncomingDamageDef, Spec, EvalParams, IncomingDamage);

 // Formula: more current posture = more vulnerable to posture damage
 float PostureRatio = CurrentPosture / FMath::Max(1.f, MaxPosture);
 float Result = IncomingDamage * (1.0f + PostureRatio * 0.5f);

 return FMath::Max(0.f, Result);
}
```


### Macro Version

If you prefer the `DECLARE_ATTRIBUTE_CAPTUREDEF` / `DEFINE_ATTRIBUTE_CAPTUREDEF` macros (which also store the `FProperty*` for potential ExecutionCalculation use):

```cpp
// PostureDamageMMC.h — add inside class body
protected:
 DECLARE_ATTRIBUTE_CAPTUREDEF(CurrentPosture);
 DECLARE_ATTRIBUTE_CAPTUREDEF(MaxPosture);
 DECLARE_ATTRIBUTE_CAPTUREDEF(IncomingDamage);
```

```cpp
// PostureDamageMMC.cpp – constructor
UPostureDamageMMC::UPostureDamageMMC()
{
 DEFINE_ATTRIBUTE_CAPTUREDEF(UMyAttributeSet, CurrentPosture, Target, false);
 RelevantAttributesToCapture.Add(CurrentPostureDef);

 DEFINE_ATTRIBUTE_CAPTUREDEF(UMyAttributeSet, MaxPosture, Target, false);
 RelevantAttributesToCapture.Add(MaxPostureDef);

 DEFINE_ATTRIBUTE_CAPTUREDEF(UMyAttributeSet, IncomingDamage, Source, false);
 RelevantAttributesToCapture.Add(IncomingDamageDef);
}
```

[!tip]
`DECLARE_ATTRIBUTE_CAPTUREDEF(CurrentPosture)` creates two variables: `CurrentPostureProperty` (the `FProperty*`) and `CurrentPostureDef` (the `FGameplayEffectAttributeCaptureDefinition`). You use `CurrentPostureDef` to reference the capture and `CurrentPostureProperty` if you need the raw property for output modifiers.

The macros expand to the same code as the manual version. The only extra benefit is they keep the `FProperty*` around — you'd need to store it manually otherwise.

## Setting It Up in the GE Asset

  1. Create a Gameplay Effect


  1. Add a **Modifier** in the `Modifiers` array:


  • **Attribute**: pick your attribute (e.g., `PostureDamage`)


  • **Modifier Op**: `Add` (for damage) or `Override` (for setting values)


  • **Magnitude**: `Custom Calculation Class`


  1. Pick your MMC class (or Blueprint)


  1. Optionally set **Coefficient**, **PreMultiplyAdditiveValue**, **PostMultiplyAdditiveValue**


  1. Done — the engine calls `CalculateBaseMagnitude` every time this effect applies

## Common Mistakes & Pitfalls

### 1. Reading an attribute you never captured
```cpp
// ❌ GetCapturedAttributeMagnitude returns false silently
float Val = 0.f;
GetCapturedAttributeMagnitude(SomeDef, Spec, EvalParams, Val);

// ✅ Add to constructor:
SomeDef.AttributeToCapture = UMyAttributeSet::GetSomeValueAttribute();
SomeDef.AttributeSource = EGameplayEffectAttributeCaptureSource::Source;
SomeDef.bSnapshot = false;
RelevantAttributesToCapture.Add(SomeDef);
```

### 2. Forgetting the `_Implementation` suffix
`BlueprintNativeEvent` functions use a pattern where the engine generates the plain function and you override `_Implementation`.
```cpp
// ❌ Won't override
float CalculateBaseMagnitude(const FGameplayEffectSpec& Spec) const;

// ✅ Correct
float CalculateBaseMagnitude_Implementation(const FGameplayEffectSpec& Spec) const override;
```

### 3. Using snapshot when you mean live
Snapshot captures the attribute value at *spec creation time*. For instant effects (frame-zero execution), snapshot vs live doesn't matter. For delayed/projectile/periodic effects, it does:

| Timing | Snapshot captures at | Live captures at |
|---|---|---|
| Instant GE | Same frame | Same frame |
| Projectile (shot → hit) | When shot | When hit |
| DOT tick N | When effect was created | Right now at tick N |

### 4. Not setting SourceTags / TargetTags in EvalParams
If you leave `EvalParams.SourceTags` and `TargetTags` as `nullptr`, the captured attribute evaluation will not filter modifiers by tags. This means all mods that affect the attribute count, even ones that don't apply to the current source/target context.

```cpp
// ❌ Misses tag filtering
FAggregatorEvaluateParameters EvalParams;
// SourceTags and TargetTags are nullptr — includes ALL mods

// ✅ Correct
FAggregatorEvaluateParameters EvalParams;
EvalParams.SourceTags = Spec.CapturedSourceTags.GetAggregatedTags();
EvalParams.TargetTags = Spec.CapturedTargetTags.GetAggregatedTags();
```

### 5. Assuming IncludePredictiveMods is true
Default is `false`. If your game uses prediction and you want client-predicted mods to count in the captured value, set it to `true`.

### 6. Using MMC when you need multiple modifier outputs
An MMC returns ONE float for ONE modifier. If you need to modify multiple attributes from a single effect execution, use `GameplayEffectExecutionCalculation` instead — it can emit any number of `FGameplayModifierEvaluatedData` outputs.

### 7. Not checking the return of GetCapturedAttributeMagnitude
The function returns `false` if the capture spec doesn't exist. In development, log the error:
```cpp
float Val = 0.f;
if (!GetCapturedAttributeMagnitude(Def, Spec, EvalParams, Val))
{
 UE_LOG(LogTemp, Warning, TEXT("PostureDamageMMC: Failed to capture attribute"));
 return 0.f;
}
```

### 8. DELEGATE vs DECLARE typo in macros
The macro is `DECLARE_ATTRIBUTE_CAPTUREDEF(P)` — many developers type `DELEGATE` out of habit from other UE macros. The compiler catches this, but it's a common frustration.

## When to Use vs Not Use

| Use MMC When | Use ExecutionCalculation When |
|---|---|
| One modifier output | Multiple modifier outputs |
| Complex math but single result | Need to apply conditional GEs |
| Designer-friendly tuning via Coefficient | Need direct ASC access for complex logic |
| Clean capture → formula → result | Multiple outputs with runtime branching |
