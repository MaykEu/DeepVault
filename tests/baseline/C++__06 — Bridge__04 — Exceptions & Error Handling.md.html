Exceptions & Error Handling

Prerequisites: 04 — RAII & The Rule of Five (coming soon) — exceptions rely on destructors.

UE: disables exceptions. This note explains what they are and why UE replaces them.

Why

C error handling requires checking every return code. Forget one check = silent bug. C++ exceptions automate cleanup: when something fails, the stack UNWINDS through every function, calling destructors along the way, until a catch block handles the error. No ignored return code possible.

Stack Unwinding

void Level3() {
 std::string data = "important";  // has destructor
 throw std::runtime_error("oops");
 // data's destructor IS called during unwind
}
void Level2() { Level3(); }
void Level1() {
 try { Level2(); }
 catch (const std::runtime_error& e) {
     // Level2+Level3 locals already destroyed
 }
}

Each frame's cleanup code runs destructors in reverse construction order. The runtime walks the stack using exception tables (.eh_frame on Linux, .pdata/.xdata on Windows) mapping PC addresses to cleanup actions.

Throwing and Catching

try {
 if (x < 0) throw std::invalid_argument("negative");
 if (x == 0) throw std::runtime_error("zero");
} catch (const std::invalid_argument& e) {
 // specific
} catch (const std::runtime_error& e) {
 // general
} catch (...) {
 // catch-all (use sparingly)
}

Always catch by const reference — avoids slicing.

Exception hierarchy: 

std::exception
├── std::logic_error (preventable)
│   ├── invalid_argument, domain_error, out_of_range
└── std::runtime_error (unpreventable)
 ├── range_error, overflow_error, system_error

Exception Safety Guarantees

The C++ standard defines three levels of exception safety. Every function falls into one of these categories — and the category determines how callers can use it safely.

Level 1 — No-Throw Guarantee

The operation cannot fail. No exception will escape.

// \\u2705 NO-THROW: Operations guaranteed to succeed
~MyClass();                    // destructors are implicitly noexcept
int x = 42;                    // built-in operations never throw
std::swap(a, b);               // typically noexcept (uses move, not copy)
obj.swap(other);               // custom swap should always be noexcept

Rule: Destructors, move constructors, move assignment, and swap() should ALWAYS be noexcept. The standard library checks noexcept on move operations — if your move constructor can throw, std::vector will COPY instead of MOVE on reallocation, destroying performance.

// \\u274c TRAP: Movable type without noexcept move
class MyType {
 std::string data;
public:
 MyType(MyType&& other) : data(std::move(other.data)) {} // NOT noexcept by default!
 // std::vector<MyType> will COPY on reallocation, not MOVE
};
// \\u2705 FIX: Explicit noexcept
MyType(MyType&& other) noexcept : data(std::move(other.data)) {}

Level 2 — Strong Guarantee (Commit-or-Rollback)

The operation succeeds completely OR fails and leaves the program state UNCHANGED.

// \\u2705 STRONG GUARANTEE: Copy-and-swap idiom
class StringList {
 std::vector<std::string> items;
public:
 void AddItem(const std::string& s) {
     auto temp = items;           // 1. Copy current state
     temp.push_back(s);           // 2. Modify COPY (may throw here)
     items = std::move(temp);     // 3. Commit — swap is noexcept
 }
 // If push_back throws: temp and items are destroyed, items unchanged
};

The copy-and-swap pattern: copy the state, modify the copy, noexcept-swap the copy into place. If the modification throws, the copy is destroyed and the original is untouched.

Level 3 — Basic Guarantee

If an exception is thrown, no resources leak and objects remain in a VALID (but unspecified) state.

// \\u2705 BASIC GUARANTEE: No leaks, but state may have changed
void SendMessages(const std::vector<Message>& msgs) {
 for (const auto& m : msgs) {
     socket.send(m); // If send() throws after 5 successes...
     // 5 messages sent, rest not sent. No leaks. State is valid, but partial.
     processed++;
 }
}

The basic guarantee is the minimum acceptable level. After failure, you can safely destroy the object, but you can't assume any particular state was achieved.

The Trap — Exception Safety Is Transitive

// \\u274c TRAP: One non-safe function poisons its caller
void UnsafeFunction() {
 items[0].mutate(); // changes items[0]
 items[1].mutate(); // if this throws, items[0] is already mutated — no rollback
}
void Caller() {
 UnsafeFunction(); // Caller's strong guarantee is GONE
}

Exception safety is NOT compositional: one basic-guarantee function inside a strong-guarantee function makes the whole thing basic at best. You must audit the entire call chain.

Auditing a Call Chain — Concrete Example

// We want SaveGame() to have the STRONG guarantee
bool SaveGame(const GameState& state) {
 auto backup = m_CurrentFile;              // Step 1: copy path (noexcept)
 auto tempFile = CreateTempFile(backup);    // Step 2: may throw (basic guarantee from OS)
 WriteHeader(tempFile, state.version);      // Step 3: may throw (basic)
 WriteBody(tempFile, state.data);           // Step 4: may throw (basic)
 AtomicReplace(backup, tempFile);           // Step 5: noexcept (OS atomic rename)
 m_CurrentFile = backup;                    // Step 6: noexcept
 return true;
}

Audit: Step 2 throws → backup local variable destroyed, no harm. Step 3 or 4 throws → tempFile exists on disk but backup is untouched, m_CurrentFile unchanged. But: Step 4 succeeds, Step 5 throws → tempFile already contains correct data, Step 5 (atomic rename) fails because disk is full. The old save file is still intact (Step 5 is atomic). Result: strong guarantee achieved.

Now the trap version:

bool BadSaveGame(const GameState& state) {
 TruncateFile(m_CurrentFile);  // Step 1: DESTROYS old data — cannot roll back!
 WriteBody(m_CurrentFile, state.data); // Step 2: if this throws, file is EMPTY
 return true;
}

Audit: Step 1 destroys the old save. Step 2 throws. File is now truncated with no data. Result: NOT EVEN BASIC guarantee — state is corrupted. Fix: never mutate in-place. Always write to a temp, then atomically replace.

When to Use Each Level

LevelWhenExample
No-throwDestructors, moves, swaps~File(), unique_ptr::reset()
StrongState-modifying operations where partial state is meaninglessDatabase::AddRecord(), GameState::ApplyPatch()
BasicStreaming operations, loops where partial progress is acceptableLogger::WriteBatch(), NetworkSocket::SendPackets()

The strong guarantee is expensive (copy entire state). Use it when partial state is genuinely unacceptable — saving a file, applying a configuration change, committing a database transaction. For most gameplay code, the basic guarantee is sufficient: a partially-updated particle system that gets destroyed next frame is fine.

noexcept as a Compile-Time Query

// noexcept operator: tells you if an expression can throw
static_assert(noexcept(std::swap(a, b)));      // true — swap is noexcept
static_assert(!noexcept(std::vector<int>().push_back(5))); // false — may throw (bad_alloc)
// noexcept specifier: PROMISES no exception escapes (violation → std::terminate)
void CriticalPath() noexcept {
 // If an exception escapes here, std::terminate() is called immediately
}

std::move_if_noexcept(obj) returns an rvalue reference (enabling move) if obj's move constructor is noexcept; otherwise returns an lvalue reference (forcing copy). This is how std::vector decides whether to move or copy during reallocation.

Designing Custom Exception Types

// \\u2705 Custom exception with WHAT and WHERE
class FileError : public std::runtime_error {
 std::filesystem::path m_path;
 int m_errno;
public:
 FileError(std::filesystem::path p, int err)
     : std::runtime_error(buildMessage(p, err))
     , m_path(std::move(p)), m_errno(err) {}
 
 const auto& path() const noexcept { return m_path; }
 int errorCode() const noexcept { return m_errno; }
 
private:
 static std::string buildMessage(const std::filesystem::path& p, int err) {
     return std::format("File '{}': {} ({})", p.string(), std::strerror(err), err);
 }
};
// Usage — catch for specific info, fall back to what() for log:
try { /* ... */ }
catch (const FileError& e) {
 std::cerr << "Failed to access " << e.path() << ": " << e.what() << "\n";
}
catch (const std::exception& e) {
 std::cerr << "Unknown error: " << e.what() << "\n";
}

Rules for custom exceptions:

  1. Inherit from std::runtime_error (not std::exception directly) — it provides the what() string infrastructure
  2. Store context in the exception object — file path, error code, line number. The catch site may need more than a string message
  3. Make accessors noexcept — exception objects may be copied during unwinding; accessors must not throw
  4. Use std::format for messages — cleaner than std::ostringstream
  5. Keep the hierarchy flat — deep exception hierarchies (FileNotFoundError → FileError → IOError → RuntimeError) sound elegant but catch sites rarely need that granularity. Two levels: your base domain error → specific error types.

Why UE Disables Exceptions

  1. Binary size: unwind tables add ~10-15%
  2. Predictability: unwind time unbounded — bad for 60fps
  3. Console platforms: historically broken exception support
  4. Philosophy: prefer explicit: check(), ensure(), verify()
check(ptr != nullptr);           // crash debug, compile-out shipping
ensure(ptr != nullptr);          // log + continue
verify(ptr != nullptr);          // always evaluate
ensureMsgf(ptr, TEXT("null %d"), line);

Two-Way Explanation

Simple

Exceptions are emergency parachutes. Normal code runs line by line (free fall). Something wrong → pull cord (throw) → float to ground (catch), passing every floor (stack unwinding) where cleanup crews work (destructors).

Technical

throw expr copies exception to heap, triggers unwind via exception tables. Two-phase: search (find handler) → cleanup (run destructors + transfer). catch(const T&) matches type — first match wins. std::uncaught_exceptions() returns in-flight count. Itanium C++ ABI uses .eh_frame for unwind info.
