From Source to Running Program — C++ Edition

> [!info] Bridge Note: connects 01 — C++ vs UE (coming soon) to the full C++ pipeline.

Why

You write main(). The OS runs it. Between those two events, four stages + the OS loader transform text into executing instructions. Understanding this pipeline means understanding where every error comes from and what your program inherits from the environment.

The C++ Pipeline

`` hello.cpp Source text ↓ Preprocessor (#include, #define, #ifdef) hello.i Single translation unit (~25K lines for iostream) ↓ Compiler (C++ → AST → IR → assembly) hello.s Human-readable CPU instructions ↓ Assembler (assembly → machine code) hello.o Binary + symbol table + relocations ↓ Linker (resolve symbols across .o + libraries) hello.exe Executable (ELF/PE/Mach-O) ↓ OS Loader (create process, map segments) Running main() executes `

Stage 1: Preprocessor

#include copy-pastes entire headers. #define does text replacement. #ifdef conditional compilation. The preprocessor doesn't understand C++ — it's pure text manipulation. Output: a single giant .i file.

Stage 2: Compiler

C++ → AST → Intermediate Representation (GIMPLE/LLVM IR) → target assembly. Optimizations happen here: inlining, dead code elimination, loop unrolling, vectorization.

Stage 3: Assembler

Assembly text → machine code bytes → .o object file with symbol table (what this file PROVIDES and REQUIRES).

Stage 4: Linker

Combines object files + libraries. Resolves every "require" to a "provide." Produces executable. Dynamic linking defers resolution to runtime via PLT/GOT.

Stage 5: OS Loader

Creates process with private virtual address space. Maps .text (code), .data (globals), .bss, stack, heap. Loads dynamic libraries. Jumps to _start → __libc_start_main → main().

What Your Program Inherits

  • argc/argv — command-line arguments
  • Environment — getenv("PATH") etc.
  • Standard streams — stdin, stdout, stderr (file descriptors 0, 1, 2)
  • Signal handlers — default handlers for SIGSEGV, SIGINT, etc.
  • C++ runtime — statics initialized, atexit registered

Two-Way Explanation

Simple

Your .cpp goes through four transformations: copy-paste headers together → translate to CPU language → convert to binary → staple all pieces into one executable. Double-click, the OS creates a private sandbox for your program and starts executing.

Technical

Phase 1-4: preprocessing → translation unit. Phase 5-7: C++ → AST → IR → assembly. Phase 8: assembly → .o (ELF/COFF). Phase 9: linking + relocation. OS: execve → ELF loader → mmap segments → _start → __libc_start_main → main. UE: UBT orchestrates this across modules with UHT injecting generated headers.

ODR — The One Definition Rule

The ODR says: every entity in your program must have exactly one definition. Variables and functions can have many declarations (headers) but only one definition (one .cpp file). Inline functions, templates, and constexpr variables are exceptions — they can be defined in multiple TUs as long as every definition is identical. 
// widget.h

int g_counter = 0;  // ❌ ODR violation if included in multiple .cpp files

inline int g_counter = 0;  // ✅ OK — inline permits multiple definitions

void helper() { }  // ❌ ODR violation (non-inline function in header!)

inline void helper() { }  // ✅ OK

```

The violation is silently accepted by the linker (no diagnostic required) — your program may crash, produce wrong results, or work by accident depending on which definition the linker picks. This is why headers use `inline` and `#ifndef` guards.

## Name Mangling

C++ compilers translate function names into unique symbols by encoding the namespace, class, parameter types, and const/volatile qualifiers:

```
void foo(int)           → _Z3fooi       (Z3 = 3-char name, foo = name, i = int)
void foo(double)        → _Z3food       (d = double)
void foo(int, double)   → _Z3fooid      (i = int, d = double)
void MyClass::foo()     → _ZN7MyClass3fooEv  (N = nested, 7MyClass = class, 3foo, E = end, v = void)
```

This is how overloading works at the link level — the linker sees different symbols, so there's no ambiguity. `extern "C"` disables mangling:

```cpp
extern "C" void foo(int);  // Symbol: foo (no mangling)
```

Without mangling, you can't overload `extern "C"` functions (the linker would see duplicate `foo` symbols). This is how C++ interfaces with C libraries and how dynamic library symbol lookup (`dlsym`) finds functions by name.
