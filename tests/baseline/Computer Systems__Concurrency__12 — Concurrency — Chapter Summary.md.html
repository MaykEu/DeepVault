Why This Chapter Matters

Modern CPUs have more cores than ever, but a single-core game runs at exactly 1/N of the available performance. Concurrency is the art of splitting work across cores — and not corrupting your data in the process. This chapter covers every tool in the toolbox: threads, mutexes, atomics, lock-free data structures, condition variables, work stealing, and the OS scheduler that makes it all possible.

The Concurrency Ladder

`` Level 1: No concurrency — single-threaded, simple, slow Level 2: Job system — fire-and-forget tasks, no shared state Level 3: Mutexes — protect shared data, careful of deadlocks Level 4: Atomics — lock-free counters, flags, SPSC queues Level 5: Lock-free structures — CAS loops, hazard pointers Level 6: Full parallelization — work stealing, NUMA-aware ` Each level trades simplicity for performance. Most game engines operate at Level 3-4: a job system for parallel work, mutexes for shared resources, and atomics for performance-critical counters.

Deadlock requires all four conditions simultaneously. Break any one:

The Game Engine Concurrency Model

Most game engines use a hybrid approach: ` Main Thread (Game Thread) │ ├── Render Thread (command generation) │ └── GPU (async compute + graphics) │ ├── Job System (thread pool, work stealing) │ ├── Physics jobs │ ├── Animation jobs │ ├── Audio jobs │ └── Asset streaming jobs │ └── Network Thread (send/recv, message serialization) ` Rule: the game thread updates game state; worker threads process data; lock-free queues communicate between them. Shared mutable state is the enemy — minimize it.

Two-Way Explanation

Simple

Concurrency is having multiple cooks in the same kitchen. Each cook (thread) can work independently on their own task — chopping vegetables, boiling water, seasoning sauce. But if two cooks reach for the same knife (shared data) at the same time, you get chaos. A mutex is a "one cook at a time" rule for a specific tool. Atomics are special tools that are safe to grab without rules — like a self-stirring pot. The scheduler is the head chef deciding who works on which station. Deadlock is when Cook A is waiting for the knife Cook B has, and Cook B is waiting for the pan Cook A has — neither can proceed. The fix: always grab tools in the same order, or grab all tools at once. Lock-free programming is designing tools so no one ever has to wait — like a conveyor belt (SPSC queue) where one person places items and another takes them, never colliding.

Technical

A process's threads share the same virtual address space but have independent register state and stack. The OS scheduler (CFS on Linux, ntoskrnl on Windows) implements preemptive multitasking via timer interrupts: the scheduler tick fires, the current thread context is saved (registers, PC, stack pointer), and the scheduler selects the next thread from the runqueue. SMT (Hyper-Threading) exposes two logical cores per physical core sharing execution units — good for hiding memory latency, bad for compute-bound threads that fight over ALUs. Mutual exclusion: std::mutex uses a futex (Linux) or SRWLOCK (Windows) — an atomic variable in user space with kernel fallback on contention. std::atomic provides lock-free operations with configurable memory ordering: relaxed (no ordering), acquire/release (one-way ordering for message passing), and sequentially consistent (total global order, default — and expensive). Deadlock prevention: std::lock uses a try-and-backoff algorithm to acquire multiple mutexes atomically. Lock-free data structures use CAS (compare_exchange_strong) loops: read current value, compute new value, atomically swap if unchanged. The ABA problem arises when a pointer is freed and reallocated between read and CAS — solved with tagged pointers or hazard pointers. False sharing: two independent variables on the same 64-byte cache line cause cache-coherency traffic between cores — fix with padding (alignas(64)) or per-core data. Amdahl's Law: speedup = 1 / (S + (1-S)/N), where S is the serial fraction — even with infinite cores, a program with 5% serial code maxes out at 20× speedup.

Exercises

  1. Amdahl's Law applied: Your game loop is: 2 ms serial (game state update), 8 ms parallel (physics on 8 cores), 2 ms serial (render command generation). What's the maximum speedup if you had infinite cores? How many cores do you need to reach 90% of that maximum?
  1. False sharing detector: Write two counters in adjacent bytes. Have thread A increment counter 1 (1 billion times) and thread B increment counter 2 (1 billion times). Measure time. Then add alignas(64) padding between them and measure again. Explain the difference — what's happening on the cache coherence bus?
  1. Lock-free SPSC queue: Implement a bounded single-producer, single-consumer queue using std::atomic for head and tail indices. The producer writes to buffer[tail] and advances tail; the consumer reads buffer[head] and advances head. What memory ordering do you need for head and tail? Test with one producer and one consumer thread transferring 10 million items.
  1. Deadlock construction: Write a program with two mutexes and two threads. Thread A locks mutex1 then mutex2. Thread B locks mutex2 then mutex1. Deliberately trigger deadlock. Then fix it with std::lock or by enforcing a lock ordering. How does std::lock avoid deadlock?
  1. Design: Design a job system for 16 cores. Jobs have dependencies (Job B depends on Job A). Jobs are submitted to per-thread queues and idle threads steal from busy queues. How do you handle dependency resolution? What happens if a thread is waiting on a dependency — should it spin or sleep? How does UE4's FQueuedThreadPool and TaskGraph` system handle this?

Synthesis Questions

  1. System design: You're building a game engine for 16-core CPUs. Your profiling shows the main thread is 60% busy (serial), parallel workers are 95% busy, and there's a 2% lock contention rate on the shared task queue. Using Amdahl's Law, what's the maximum speedup from parallelization? What bottlenecks would you address first?
  1. Cross-layer analysis: A player reports that their game hitches every 30 seconds. Using perf/VTune, you see a burst of 200+ context switches within 50 ms, followed by a mutex contention spike. Trace the chain: which OS scheduler behavior causes the context switches? Which mutex pattern causes the contention? How does cache warmup after rescheduling make the hitch worse?
  1. Lock-free vs mutex tradeoff: Your audio thread (SCHED_FIFO, priority 80) reads from a ring buffer filled by the game thread (SCHED_OTHER, priority 0). Under what exact conditions does a mutex-protected buffer cause priority inversion? Why does an SPSC lock-free ring buffer eliminate this risk entirely?

Common Pitfalls

  1. Tuning without profiling: Never guess where the contention is. Use VTune, perf, or Tracy to measure actual lock contention, cache misses, and context switch rates.
  1. Copy-pasting synchronization patterns: What works for a job system (lock-free SPSC queue) doesn't work for a shared game state (mutex or RWLock). Understand the access pattern before choosing the primitive.
  1. Assuming SMT gives 2× throughput: Hyperthreading shares execution units. Two threads on one core rarely exceed 1.3× a single thread. Sizing thread pools requires accounting for physical cores, not logical threads.
