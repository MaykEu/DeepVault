ApplyGameplayEffectSpec Pipeline

Overview

When a GameplayEffect is applied — whether from an ability, a hit event, or a GE component — the following happens in order. Understanding this pipeline is essential because it's where MMCs run, snapshots are taken, durations are set, and prediction keys are reconciled. > [!info] Source > GameplayEffect.cpp:4171 — FActiveGameplayEffectsContainer::ApplyGameplayEffectSpec

Step-by-Step Detail

Step 1-2: Stacking

ApplyGameplayEffectSpec first checks if a stackable GE with the same definition already exists via FindStackableActiveGameplayEffect(Spec). If a stackable GE exists:
  • Prediction CVar: If bAllowPredictiveApplicationOfStackingGameplayEffects is false (default) and the client is not authoritative, the stacking application is rejected (return nullptr). On the server, the prediction key is invalidated (InPredictionKey = FPredictionKey()).
  • HandleActiveGameplayEffectStackOverflow is called in two cases:
1. Legacy — if we've ALREADY reached the stack limit (bStackCountAtLimit) 2. Overflow — if the new total exceeds the limit AND HasActiveGameplayEffectOverflowBehavior(EActiveGameplayEffectOverflowBehavior::HandleOverflowingStacksAlways) is true If overflow handling returns false, the application is denied.
  • The existing GE's GrantedAbilitySpecs are preserved (swap out, replace Spec, swap back). Abilities are only granted on first application, not on stack.
  • DynamicGrantedTags and DynamicAssetTags are ensureMsgf'ed to match between old and new stacks — mismatches are not properly resolved.
  • Linked aggregator callbacks are unregistered before replacing the spec (they're re-registered later).
  • Duration extension: If StackDurationRefreshPolicy == ExtendDuration, the remaining time is cached (CarryOverDuration) and added to the new duration.
  • Duration refresh: If the prediction key is a locally-generated client key, OR the policy is NeverRefresh, the duration timer is NOT reset. Otherwise, RestartActiveGameplayEffectDuration is called.
  • Period reset: If StackPeriodResetPolicy == NeverReset, the period timer is NOT reset.
If no stackable GE exists:
  • A new FActiveGameplayEffectHandle is generated.
  • The GE is added to the array — either in the main GameplayEffects_Internal` array OR, if the array has 0 slack (full), allocated on the pending GE linked list:
// Pending GE mechanism:

// Each active GE has a PendingNext pointer forming a linked list.

// When the main array is full, new GEs are appended to this list.

// After the scope lock releases, the list is merged into the main array.

// This prevents reallocation of the array while iterating it.

```

  • `HandleActiveGameplayEffectStackOverflow` is called with a temporary spec (count=0), then the new stack count is clamped to `StackLimitCount`.


### pending GE linked list

When `GameplayEffects_Internal.GetSlack() <= 0`, the container is scope-locked and can't reallocate. Instead of crashing, it uses a pre-allocated linked list:
```
check(PendingGameplayEffectNext);
if (*PendingGameplayEffectNext == nullptr)
 AppliedActiveGE = new FActiveGameplayEffect(NewHandle, Spec, ...)
else
 **PendingGameplayEffectNext = FActiveGameplayEffect(NewHandle, Spec, ...)  // move into existing allocation
```
The linked list is merged into the main array once the scope lock releases. This is purely an internal memory management detail — your code never sees this.

### Step 3-4: Target Tags and Attributes

These are captured from the **target's** ASC at the moment of application. Before that, a global callback fires:

```cpp
// GameplayEffect.cpp:4378

UAbilitySystemGlobals::Get().SetCurrentAppliedGE(&AppliedActiveGE->Spec);
UAbilitySystemGlobals::Get().GlobalPreGameplayEffectSpecApply(AppliedEffectSpec, Owner);
```

`GlobalPreGameplayEffectSpecApply` is a project-wide callback you can hook via `UAbilitySystemGlobals`. Default does nothing, but you can override it to modify specs globally before they take effect.

Then:
```cpp
// GameplayEffect.cpp:4382-4388

AppliedEffectSpec.CapturedTargetTags.GetActorTags().Reset();
Owner->GetOwnedGameplayTags(AppliedEffectSpec.CapturedTargetTags.GetActorTags());

AppliedEffectSpec.CaptureAttributeDataFromTarget(Owner);
AppliedEffectSpec.CalculateModifierMagnitudes();
```

`CaptureAttributeDataFromTarget` fills in the target-side capture specs with references to the actual FAggregators on the target's ASC.

Source-side captures were already filled in during spec creation (`MakeOutgoingSpec`).

### Step 5: CalculateModifierMagnitudes — Where MMC Runs

```cpp
// GameplayEffect.cpp:2033
void FGameplayEffectSpec::CalculateModifierMagnitudes()
{
 for (int32 ModIdx = 0; ModIdx < Modifiers.Num(); ++ModIdx)
 {
     const FGameplayModifierInfo& ModDef = Def->Modifiers[ModIdx];
     FModifierSpec& ModSpec = Modifiers[ModIdx];

     if (ModDef.ModifierMagnitude.AttemptCalculateMagnitude(*this, ModSpec.EvaluatedMagnitude) == false)
     {
         ModSpec.EvaluatedMagnitude = 0.f;
     }
 }
}
```

This iterates every modifier on the GE and evaluates:

| Magnitude Type | What happens | Evaluated when |
|---|---|---|
| **ScalableFloat** | `Coefficient.GetValueAtLevel(Level, Context)` → returns float | Now |
| **AttributeBased** | Captures the attribute's current value from the aggregator | Now |
| **CustomCalculationClass** | Calls `CalcCDO->CalculateBaseMagnitude(Spec)` — **your MMC** | Now |
| **SetByCaller** | Looks up a tag/name from the spec's SetByCaller map | Now |

The result is stored in `FModifierSpec::EvaluatedMagnitude` and later used when the modifier actually applies to the FAggregator.

### Step 6: ModifiedAttributes List

For **duration effects with no period** and **instant effects with a period** (not standard, but possible), the system builds a `ModifiedAttributes` list **before registering callbacks**:

```cpp
const bool HasModifiedAttributes = AppliedEffectSpec.ModifiedAttributes.Num() > 0;
const bool HasDurationAndNoPeriod = (DurationPolicy == HasDuration && Period == NO_PERIOD);
const bool HasPeriodAndNoDuration = (DurationPolicy == Instant && Period > NO_PERIOD);
const bool ShouldBuild = !HasModifiedAttributes && (HasDurationAndNoPeriod || HasPeriodAndNoDuration);
```

If the conditions are met, the system iterates all modifier definitions and sums their evaluated magnitudes into a `ModifiedAttributes` array. Each entry is a `FGameplayEffectModifiedAttribute` with just the attribute and total magnitude.

This is used for:

  • Generating `GameplayCue` parameters with magnitude info (e.g., a GC that shows the heal number)


  • Tracking total modifier contributions per attribute


This happens **only once** per GE application, and only for durations that don't have periodic ticks (those use the execution flow's more thorough per-tick evaluation instead).

### Step 7: Linked Aggregator Callbacks

For LIVE (non-snapshot) captures, the spec registers callbacks so that if the captured attribute changes while the GE is active, the modifier magnitude can be recalculated:

```cpp
// GameplayEffect.cpp:4442
AppliedEffectSpec.CapturedRelevantAttributes.RegisterLinkedAggregatorCallbacks(AppliedActiveGE->Handle);
```

This is what makes `Duration` and `Infinite` effects "respond" to attribute changes even after they've been applied.

### Step 8-9: Duration Calculation + Timer

Duration is evaluated in multiple stages:

**Stage 1: Base duration from definition**
```cpp
float DefCalcDuration = 0.f;
if (AppliedEffectSpec.AttemptCalculateDurationFromDef(DefCalcDuration))
{
 AppliedEffectSpec.SetDuration(DefCalcDuration, false);
}
else if (Def->DurationMagnitude.GetMagnitudeCalculationType() == SetByCaller)
{
 // Fallback: SetByCaller duration

 Def->DurationMagnitude.AttemptCalculateMagnitude(AppliedEffectSpec, AppliedEffectSpec.Duration);
}
```

**Stage 2: Apply duration modifier mods**
```cpp
float FinalDuration = AppliedEffectSpec.CalculateModifiedDuration();
// Applies "duration +10%" type mods from other active GEs on this ASC

if (CarryOverDuration > 0.0f)
 FinalDuration += CarryOverDuration;  // stacking extension

```

**Stage 3: Clamp to MaxDuration**
```cpp
float SpecMaxDuration = 0.0f;
if (!AppliedEffectSpec.AttemptCalculateMaxDurationFromDef(SpecMaxDuration))
{
 // Fallback: SetByCaller max duration

 Def->MaxDurationMagnitude.AttemptCalculateMagnitude(AppliedEffectSpec, SpecMaxDuration);
}

if (FinalDuration <= 0.f)
 FinalDuration = 0.1f;  // minimum clamp (logged as error)

else if (SpecMaxDuration > 0.0f && FinalDuration > SpecMaxDuration)
 FinalDuration = SpecMaxDuration;

AppliedEffectSpec.SetDuration(FinalDuration, false);
OnDurationChange(*AppliedActiveGE);  // broadcast to listeners

```

**Stage 4: Register timer**
```cpp
if (Owner && bSetDurationTimer)
{
 FTimerDelegate Delegate = FTimerDelegate::CreateUObject(Owner,
     &UAbilitySystemComponent::CheckDurationExpired, AppliedActiveGE->Handle);
 TimerManager.SetTimer(AppliedActiveGE->DurationHandle, Delegate, FinalDuration, false);

 if (!ensureMsgf(AppliedActiveGE->DurationHandle.IsValid(), ...))
 {
     // Fallback: force next tick

     TimerManager.SetTimerForNextTick(Delegate);
 }
}
```

Duration magnitude supports the same types as modifiers: ScalableFloat, AttributeBased, Custom (MMC), or SetByCaller.

### Step 10: Periodic Timer

If the GE has a `Period > 0`, a repeating timer is set to fire `ExecutePeriodicEffect`:

```cpp
TimerManager.SetTimer(AppliedActiveGE->PeriodHandle, Delegate,
 AppliedEffectSpec.GetPeriod(), true);
```

If `bExecutePeriodicEffectOnApplication` is true (uncommon), the first tick fires on the next frame instead of waiting for the full period.

Periodic timers are **server-only** — clients don't predict periodic ticks.

### Step 11: Prediction Key Handling

```cpp
// GameplayEffect.cpp:4543
if (InPredictionKey.IsLocalClientKey() == false || IsNetAuthority())
{
 MarkItemDirty(*AppliedActiveGE);    // Server: mark for replication
}
else
{
 MarkArrayDirty();                    // Client: rebuild internal map
}
```

**Server**: calls `MarkItemDirty` to replicate the new GE to clients.

**Client (predicting)**: calls `MarkArrayDirty` and binds **cleanup delegates** based on stack type:

**Non-stackable or first stack:**
```cpp
// Remove all stacks once server catches up
if (!CVarFixPredictedTagApplication)
{
 // Separate delegates for caught-up and rejected:
 InPredictionKey.NewCaughtUpDelegate().BindUObject(Owner,
     &UAbilitySystemComponent::OnCaughtUpActiveGameplayEffect,
     AppliedActiveGE->Handle, RemoveAllStacks (-1));
 InPredictionKey.NewRejectedDelegate().BindUObject(Owner,
     &UAbilitySystemComponent::OnRejectedActiveGameplayEffect,
     AppliedActiveGE->Handle, RemoveAllStacks (-1));
}
else
{
 // Combined delegate (CVar fix):
 InPredictionKey.NewRejectOrCaughtUpDelegate(
     FPredictionKeyEvent::CreateUObject(Owner,
         &UAbilitySystemComponent::RemoveActiveGameplayEffect_AllowClientRemoval,
         AppliedActiveGE->Handle, RemoveAllStacks (-1)));
}
```

**Stackable GE (additional stacks):**
```cpp
// OnCaughtUp or OnRejected, readjust the stack count:
InPredictionKey.NewRejectOrCaughtUpDelegate(
 FPredictionKeyEvent::CreateUObject(Owner,
     &UAbilitySystemComponent::OnPredictiveGameplayEffectStackCaughtUp,
     AppliedActiveGE->Handle));
```

The key difference: a non-stackable GE is **removed entirely** when caught up (the server's authoritative copy replaces it). A stackable GE only readjusts its stack count.

  • **Server**: calls `MarkItemDirty` to replicate the new GE to clients


  • **Client (predicting)**: calls `MarkArrayDirty` and binds cleanup delegates. When the server's replication arrives with the matching prediction key, the predicted GE is removed and replaced with the server's authoritative version


For **instant effects** on a predicting client, the spec's duration is set to `INFINITE_DURATION` (the `bTreatAsInfiniteDuration` mechanism) so the GE can be stored in the ActiveGameplayEffects container for prediction tracking.

### Step 12: InternalOnActiveGameplayEffectAdded

```cpp
// GameplayEffect.cpp:4565
const bool bInvokePredictedEffects = (Spec.Def->DurationPolicy != EGameplayEffectDurationType::Instant);
InternalOnActiveGameplayEffectAdded(*AppliedActiveGE, bInvokePredictedEffects);
```

  • **Duration/Infinite**: `bInvokePredictedEffects = true` — cues are invoked (OnActive, WhileActive) and are predicted on client


  • **Instant**: `bInvokePredictedEffects = false` — cues are NOT invoked here. They fire during `ExecuteActiveEffectsFrom` instead


Inside `InternalOnActiveGameplayEffectAdded` (line 4572):

```cpp
void FActiveGameplayEffectsContainer::InternalOnActiveGameplayEffectAdded(
 FActiveGameplayEffect& Effect, const bool bInvokePredictedEffects)
{
 // 1. Add external dependencies (MMC external dependency callbacks)
 AddCustomMagnitudeExternalDependencies(Effect);

 // 2. Notify GE components:
 const bool bActive = EffectDef->OnAddedToActiveContainer(*this, Effect);

 // 3. Effect starts INHIBITED — then the inhibition check runs
 Effect.bIsInhibited = true;
 Owner->SetActiveGameplayEffectInhibit(EffectHandle, !bActive, bInvokePredictedEffects);
}
```

The GE starts inhibited. `SetActiveGameplayEffectInhibit` runs the actual inhibition logic (tag checks, granted tags, gameplay cues), then the effect is uninhibited if bActive is true.

**For Stackable GEs**: `OnStackCountChange` is called instead, which fires stack-change delegates without re-running the full inhibition check.

## Execution Path (for Instant/Periodic)

For Instant and Periodic effects, the GE also enters the **execution** pipeline, which runs AFTER `ApplyGameplayEffectSpec`:

```
ApplyGameplayEffectSpecToSelf()
│
├── ApplyGameplayEffectSpec()    ← (the pipeline above)
│
└── if Instant:
     ExecuteGameplayEffect()    ← runs ExecuteActiveEffectsFrom
         ├── CalculateModifierMagnitudes() again
         ├── Apply modifiers to FAggregator (InternalExecuteMod)
         ├── Execute EEC (if any) ← YOUR EEC RUNS HERE
         ├── Apply conditional GEs
         └── Invoke gameplay cues
```

This is covered in detail in [[GE Execution Flow]].
