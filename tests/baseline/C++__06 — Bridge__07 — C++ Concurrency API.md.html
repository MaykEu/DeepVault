C++ Concurrency API

This note bridges the C++ standard library concurrency API to the theory covered in Concurrency Overview (coming soon). The Computer Systems notes teach WHAT threads, mutexes, and atomics ARE. This note teaches HOW to use the C++ types: std::thread, std::mutex, std::future, std::async, and friends.

Why This Matters
The C++ standard library provides a complete concurrency toolkit. std::thread launches threads. std::mutex + std::lock_guard protects shared data. std::async + std::future return values from background work. std::atomic enables lock-free programming. You can write threaded code with pthreads or Win32 threads — but std:: types are portable, RAII-safe, and compose with the rest of the standard library. Every game engine eventually wraps these in its own abstractions (UE5's FRunnableThread, FCriticalSection), but the primitives underneath are these.

Prerequisites: Processes & Threads (coming soon), Data Races & Mutexes (coming soon), Atomics & Memory Ordering (coming soon), RAII & Rule of Five (coming soon) (mutex locking IS RAII).

std::thread — Launching and Joining

#include <thread>
#include <iostream>
void Worker(int id, const std::string& msg) {
 std::cout << "Thread " << id << ": " << msg << '\n';
}
int main() {
 std::thread t1(Worker, 1, "hello");  // launches immediately
 std::thread t2(Worker, 2, "world");
 t1.join();  // wait for t1 to finish
 t2.join();  // wait for t2 to finish
 // After join: thread has completed. Safe to destroy.
}

The Join/Detach Rule

Every std::thread MUST be either join()ed or detach()ed before it's destroyed. Destroying an unjoined, undetached thread calls std::terminate() — instant death.

// ❌ UB — thread destroyed without join or detach
{
 std::thread t(Worker, 1, "oops");
} // std::terminate() called!
// ✅ join: wait for completion
void WaitForThread() {
 std::thread t(Worker, 1, "ok");
 t.join(); // block until t finishes
}
// ✅ detach: let it run independently (rarely correct)
void FireAndForget() {
 std::thread t(Worker, 1, "background");
 t.detach(); // t runs independently — you can't join it later
 // Dangerous: Worker may access destroyed stack variables of FireAndForget
}

detach() is almost always wrong. If the detached thread accesses local variables of the spawning function, those variables may be destroyed before the thread finishes. Prefer join() or std::async.

Passing Arguments

Arguments are COPIED (or moved) into the thread's storage. To pass by reference, use std::ref:

void Modify(int& value) { value = 42; }
int x = 0;
std::thread t(Modify, std::ref(x)); // pass by reference
t.join();
// x == 42

Without std::ref, x would be copied and Modify would mutate the copy — not x. The original stays unchanged.

Exception Safety for Threads

// ❌ If DoWork() throws, join() is never called → terminate()
void UnsafeThread() {
 std::thread t(Worker, 1, "data");
 DoWork(); // may throw
 t.join(); // NEVER REACHED if DoWork throws
}
// ✅ RAII wrapper pattern
class ThreadGuard {
 std::thread& t;
public:
 explicit ThreadGuard(std::thread& thread) : t(thread) {}
 ~ThreadGuard() { if (t.joinable()) t.join(); }
 ThreadGuard(const ThreadGuard&) = delete;
};
void SafeThread() {
 std::thread t(Worker, 1, "data");
 ThreadGuard guard(t); // join on scope exit, even via exception
 DoWork(); // may throw — guard's destructor still calls join()
}

Mutexes and Lock Guards — Protecting Shared Data

#include <mutex>
std::mutex m;
int shared_counter = 0;
void Increment() {
 m.lock();
 ++shared_counter;
 m.unlock(); // ❌ What if ++shared_counter throws? Unlock never called!
}
// ✅ RAII lock — never forgets to unlock
void IncrementSafe() {
 std::lock_guard<std::mutex> lock(m);
 ++shared_counter;
} // lock destroyed here → m.unlock() called automatically

The Mutex Family

The Lock Guard Family

Locking Multiple Mutexes — std::scoped_lock

std::mutex m1, m2;
// ❌ DEADLOCK POTENTIAL: Thread A locks m1 then m2. Thread B locks m2 then m1.
void Transfer_Bad(Account& from, Account& to, int amount) {
 std::lock_guard lock1(from.m);
 std::lock_guard lock2(to.m); // DEADLOCK if another thread locks to.m then from.m
 from.balance -= amount;
 to.balance += amount;
}
// ✅ std::scoped_lock: atomically locks ALL mutexes in a deadlock-free order
void Transfer_Safe(Account& from, Account& to, int amount) {
 std::scoped_lock lock(from.m, to.m); // both locked atomically
 from.balance -= amount;
 to.balance += amount;
}

std::unique_lock — Deferred Locking

std::mutex m;
// Defer lock acquisition — lock later manually
std::unique_lock<std::mutex> lock(m, std::defer_lock);
// ... do work that doesn't need the lock ...
lock.lock();   // now acquire
// ... critical section ...
lock.unlock(); // release early
// ... more non-critical work ...
lock.lock();   // re-acquire if needed

Unique to unique_lock: you can defer lock, unlock early, transfer ownership via move. Its destructor unlocks only if locked.

std::condition_variable — Signaling Between Threads

Condition variables let one thread WAIT until another thread signals that work is ready or data is available. They're used with a mutex and a predicate — never signal alone.

The Pattern

std::mutex m;
std::condition_variable cv;
std::queue<int> workQueue;
bool done = false;
// Consumer thread: wait for work
void Consumer() {
 while (true) {
     std::unique_lock<std::mutex> lock(m);
     cv.wait(lock, [] { return !workQueue.empty() || done; });
     // wait() atomically: unlocks m, sleeps, re-locks m on wakeup
     
     if (done && workQueue.empty()) break;
     
     int item = workQueue.front();
     workQueue.pop();
     lock.unlock(); // release lock before processing
     ProcessItem(item);
 }
}
// Producer thread: add work and signal
void Producer() {
 for (int i = 0; i < 100; ++i) {
     {
         std::lock_guard<std::mutex> lock(m);
         workQueue.push(i);
     }
     cv.notify_one(); // wake ONE waiting consumer
 }
 {
     std::lock_guard<std::mutex> lock(m);
     done = true;
 }
 cv.notify_all(); // wake ALL consumers (for shutdown)
}

Why the Predicate Is NOT Optional

// ❌ WRONG: wait without predicate — spurious wakeup will proceed
cv.wait(lock); // MAY return even if condition is false!
// ✅ CORRECT: wait with predicate — loop until condition is true
cv.wait(lock, [] { return !workQueue.empty(); });
// Equivalent to: while (!pred()) { cv.wait(lock); }

Spurious wakeups are real — the OS or hardware may wake a waiting thread for no reason. The predicate loop is NOT optional.

notify_one vs notify_all

FunctionUse When
notify_one()One waiting thread will handle the work — wake one, avoid thundering herd
notify_all()All waiting threads need to react — shutdown, state change affecting everyone
The trap: Notifying BEFORE releasing the mutex may cause the woken thread to immediately block waiting for the mutex (pointless wakeup). Notifying AFTER releasing the mutex is usually better:

// ✅ Better: unlock first, then notify
{
 std::lock_guard lock(m);
 workQueue.push(item);
} // lock released here
cv.notify_one(); // woken thread can immediately acquire the mutex

std::once_flag and std::call_once — Thread-Safe Initialization

std::once_flag init_flag;
ExpensiveResource* resource = nullptr;
void Initialize() {
 resource = new ExpensiveResource(/* ... */);
}
void ThreadFunc() {
 std::call_once(init_flag, Initialize); // called exactly ONCE across all threads
 resource->Use(); // guaranteed initialized before any thread reaches here
}

Before C++11, this was the "double-checked locking pattern" — notoriously difficult to get right. call_once solves it definitively.

Futures and Promises — Returning Values from Threads

std::thread doesn't return values. std::async + std::future does.

std::async — The Simplest Way to Run Work in Background

#include <future>
// Launch background work, get a future for the result
std::future<int> result = std::async(std::launch::async, [] {
 return ComputeExpensiveValue(); // runs on another thread
});
// Do other work while computation runs...
DoOtherWork();
// Block until result is ready, then get the value
int value = result.get(); // blocks if not ready; throws if the task threw

std::future Lifetime — The std::async Trap

// ❌ BLOCKS DESTRUCTOR: std::async future blocks in destructor if not consumed
{
 std::async(std::launch::async, WorkerFunc);
} // future's destructor BLOCKS until WorkerFunc completes — defeats the purpose
// ✅ Keep the future alive until you're ready to wait:
auto fut = std::async(std::launch::async, WorkerFunc);
DoOtherWork();
fut.get(); // explicit: "I'm ready to wait now"

The destructor of a std::future from std::async(std::launch::async, ...) blocks until the task completes. This is the #1 std::async gotcha.

std::promise — Manual Future Production

std::promise<int> promise;
std::future<int> future = promise.get_future();
std::thread worker([&promise] {
 try {
     int result = ComputeExpensiveValue();
     promise.set_value(result); // fulfill the promise → future.get() unblocks
 } catch (...) {
     promise.set_exception(std::current_exception()); // propagate exception to future
 }
});
int value = future.get(); // blocks until promise is fulfilled
worker.join();

std::async is std::promise + std::thread bundled together. Use std::async when you can. Use std::promise when you need manual control over when the value is produced.

std::packaged_task — A Future-Wrapped Callable

// Wrap a callable into a future-returning object
std::packaged_task<int(int, int)> task([](int a, int b) { return a + b; });
std::future<int> result = task.get_future();
// Execute the task anywhere — another thread, or even the same thread
task(40, 2); // execute now
int answer = result.get(); // 42 — no blocking, already ready

std::packaged_task is a callable wrapper that produces a std::future. It's std::promise + std::function in one. Use it in thread pools and task queues.

std::shared_future — Multiple Waiters

std::future<int> fut = std::async(std::launch::async, [] { return 42; });
std::shared_future<int> shared = fut.share(); // transfers ownership
// Multiple threads can now call shared.get() — each gets the same result
auto t1 = std::thread([shared] { int v = shared.get(); });
auto t2 = std::thread([shared] { int v = shared.get(); });

std::future::get() can only be called ONCE. std::shared_future::get() can be called many times — useful for broadcasting a result to multiple consumers.

std::atomic — Lock-Free Primitives

See Atomics & Memory Ordering (coming soon) for the full theory. Here's the C++ API mapping:

#include <atomic>
std::atomic<int> counter{0};
// Basic operations — all atomic, all lock-free on modern CPUs
counter.store(42);                    // write
int val = counter.load();             // read
int old = counter.fetch_add(1);       // read-modify-write (returns old value)
int old = counter++;                   // same as fetch_add(1)
bool success = counter.compare_exchange_strong(expected, desired);
// Memory ordering (default is seq_cst — safest, slowest):
counter.store(42, std::memory_order_release);
int val = counter.load(std::memory_order_acquire);

std::atomicTypical Use
std::atomicFlags, spinlocks
std::atomic / Counters, indices
std::atomicLock-free linked structures
std::atomic> (C++20)Reference-counted shared state
std::atomic> (C++20)Weak references in concurrent structures

Parallel Algorithms (C++17)

#include <algorithm>
#include <execution>
std::vector<int> data(1000000);
// Sequential sort
std::sort(std::execution::seq, data.begin(), data.end());
// Parallel sort (C++17)
std::sort(std::execution::par, data.begin(), data.end());
// Parallel + vectorized (C++17)
std::sort(std::execution::par_unseq, data.begin(), data.end());

Execution PolicyBehaviorWhen to Use
std::execution::seqSequential — same as no policySingle-threaded or small data
std::execution::parParallel — multiple threadsLarge data, work per element is significant
std::execution::par_unseqParallel + SIMD vectorizedMaximum throughput, no synchronization in element ops

Parallel algorithms do NOT guarantee speedup. They guarantee ATTEMPTS to parallelize. Thread creation overhead, false sharing, and data contention can make them SLOWER than sequential. Always measure.

Thread-Local Storage

thread_local int perThreadCounter = 0;
void Worker() {
 perThreadCounter++; // each thread has its OWN counter
}

thread_local creates one instance of a variable PER THREAD. In UE5, this is how stat counters accumulate per-thread before flushing to global stats.

Two-Way Explanation

Beginner: Threads let your program do multiple things at once. std::thread starts a new thread. std::mutex protects shared data — only one thread can hold the lock at a time. std::lock_guard locks on creation and unlocks automatically when it goes out of scope (RAII). std::async runs work in the background and gives you a std::future — call .get() on the future to wait for the result. std::atomic enables lock-free counters and flags — no mutex needed for simple operations.

Experienced: The C++ Thread Library (, , , , ) provides a portable, RAII-guaranteed concurrency API. std::thread models OS threads; its destructor enforces the join-or-detach invariant via std::terminate(). std::scoped_lock (C++17) applies a deadlock-avoidance algorithm (std::lock) to acquire multiple mutexes atomically — the canonical solution to the lock-ordering problem. std::async with std::launch::async guarantees a new thread; without the policy, the implementation MAY run synchronously. The std::future destructor from std::launch::async blocks ([futures.async]/5) — the most commonly missed behavior. std::atomic provides hardware-backed atomic operations with six memory orderings; the default seq_cst is the safest and most expensive. Parallel algorithms (std::execution::par) delegate to the implementation's thread pool — they're advisory, not guaranteed, and must be benchmarked. thread_local storage is per-thread; on access, the variable's initializer runs once per thread (lazy initialization with a hidden guard variable).

Exercises

  1. Thread join/detach: Write a program that creates 3 threads, each printing its ID. Use join(). What happens if you forget join()? Now try detach() — can you guarantee the threads finished before main exits?
  1. Mutex guard: Write a Counter class with Increment() and Get() methods protected by std::mutex + std::lock_guard. What would break if you used std::unique_lock without calling .lock()? What if you forgot the lock entirely?
  1. Scoped lock: Write Transfer(Account& from, Account& to, int amount) using std::scoped_lock. Create two threads that transfer in opposite directions. Does the code deadlock? Why not?
  1. Future result: Use std::async to compute the sum of a large vector in a background thread. While it runs, print progress dots to std::cout. When the future is ready, print the result. What happens if you call fut.get() twice?
  1. Atomic vs mutex benchmark: Implement a shared counter incremented by 4 threads, 1,000,000 times each. First with std::mutex + lock_guard. Then with std::atomic::fetch_add. Time both. Which is faster? Why? At what contention level does the mutex approach break even?
