UPROPERTY — When and Why

What UPROPERTY Does

UPROPERTY() is a UE macro that registers a member variable with the engine's reflection system. It's not about memory management in the traditional sense — it's about telling UE the variable exists so the engine can track it.

Registration gives the engine access to the variable for:

SystemWhat it enables
GC (Garbage Collection)Marks UObject* pointers as reachable — prevents collection
ReplicationVariables marked Replicated are synced across the network
SerializationSave/load to disk (level saves, save games)
BlueprintBlueprint can read/write the variable
EditorShows in details panel, supports undo/redo
InitializationZero-initializes on construction
RPCsFunction parameters in UFUNCTION use UPROPERTY for their types

When You NEED UPROPERTY

1. UObject pointers that you own

UPROPERTY()
UMyObject* MyObject;  // ✅ Engine roots this, prevents GC
// Without UPROPERTY:
UMyObject* MyObject;  // ❌ Can be GC'd at any time — dangling pointer

UE's GC collects any UObject that isn't reachable from a UPROPERTY() chain. If you store a UObject* without UPROPERTY(), it can be destroyed while you're still holding it.

2. Replicated variables

UPROPERTY(Replicated)
float Health;  // ✅ Replicated to clients
// Without UPROPERTY(Replicated):
float Health;  // ❌ Not replicated — stays local

For DOREPLIFETIME to find the variable, it must be UPROPERTY(Replicated).

3. Blueprint-accessible variables

UPROPERTY(BlueprintReadWrite, EditAnywhere)
int32 MaxComboCount;  // ✅ Visible and editable in Blueprint/editor
// Without UPROPERTY:
int32 MaxComboCount;  // ❌ Invisible to Blueprint entirely

4. Serialized/saved variables

UPROPERTY()
FString SaveFileName;  // ✅ Saved with the actor/level/package
// Without UPROPERTY:
FString SaveFileName;  // ❌ Lost on save

When You DON'T Need UPROPERTY

1. Pointers to struct data inside other UObjects

// Your component stores a pointer to the ASC's internal tag container:
const FGameplayTagContainer* CharacterTagContainer = nullptr;
void Init()
{
 UAbilitySystemComponent* ASC = ...;
 // ASC's ExplicitTags is a FGameplayTagContainer inside FGameplayTagCountContainer
 // inside the ASC. The ASC is a UObject rooted by its owning Actor.
 CharacterTagContainer = &ASC->GetOwnedGameplayTags();
}

This pointer doesn't need UPROPERTY() because:

  • It points to a struct (FGameplayTagContainer), not a UObject — GC doesn't track structs
  • The data lives inside the ASC, which IS a UObject rooted by the Actor — no risk of the struct being destroyed independently
  • You're not serializing, replicating, or exposing this to Blueprint

2. Raw pointers to UObjects you don't own

AActor* CachedTarget;  // ✅ OK without UPROPERTY for temporary/short-lived references

But be careful — if the AActor can be destroyed, this pointer dangles. For references that persist across frames, either use UPROPERTY() or TWeakObjectPtr<>:

UPROPERTY()
AActor* CachedTarget;  // ✅ Keeps the actor alive (if you need that)
TWeakObjectPtr<AActor> CachedTarget;  // ✅ No GC root, detects destruction

3. Transient / computed state

float CachedDeltaTime;        // ❌ No UPROPERTY needed — computed each frame
TArray<int32> TempIndices;    // ❌ No UPROPERTY needed — working data
bool bHasStarted;             // ❌ No UPROPERTY needed — internal state

If a variable is recalculated every frame, is only used in C++, and doesn't need to persist, skip UPROPERTY().

What UHT Rejects

PatternErrorWhy
UPROPERTY() const Type Var;"Const properties are not supported"UHT can't write to const variables. Remove const.
UPROPERTY() FGameplayTagContainer Ptr;"Inappropriate '' on FGameplayTagContainer"UHT only allows UObject* pointers. Use TObjectPtr<> or store the struct by value.
UPROPERTY() TSharedPtr Ptr;No direct supportUHT handles UObject* and TWeakObjectPtr, not TSharedPtr.
If you run into these, the variable probably doesn't need UPROPERTY() at all.

Lifetime Rules

UObject pointers

UPROPERTY() UObject* → Keeps it alive (GC root)
No UPROPERTY        → Can be collected at any GC cycle
TWeakObjectPtr      → No influence on lifetime, detects dangling
TStrongObjectPtr    → Always keeps it alive (non-UPROPERTY root)

Struct value members

UPROPERTY() FGameplayTagContainer → Serialized, replicated, Blueprint-accessible
No UPROPERTY                     → Not serialized, not replicated, not visible to Blueprint
                                But still alive — structs live as part of their owner

Struct pointer members

UPROPERTY() FStructType* → ❌ UHT rejects this (for non-UObject types)
No UPROPERTY            → ✅ The only valid option — but you must manage lifetime yourself

Quick Decision Guide

Is it a UObject*?
├── Do you want GC to keep it alive?
│   ├── YES → use UPROPERTY()
│   └── NO  → use TWeakObjectPtr<>
└── Do you need it in Blueprint?
 └── YES → use UPROPERTY(BlueprintReadOnly/BlueprintReadWrite)
Is it a struct by value?
├── Need replication?              → UPROPERTY(Replicated)
├── Need serialization?            → UPROPERTY()
├── Need Blueprint access?         → UPROPERTY(BlueprintReadWrite)
└── Internal working data only?    → ✅ Skip UPROPERTY entirely
Is it a pointer to a struct?
└── Non-owning pointer to data inside another UObject?
 └── ✅ Skip UPROPERTY (UHT won't allow it anyway)

Common Mistakes

1. Missing UPROPERTY on a UObject* — random crashes

// ❌ Crashes when UE GC runs during gameplay
UMyObject* MyThing;
// ✅ GC roots it — stays alive
UPROPERTY()
UMyObject* MyThing;

2. UPROPERTY on something that doesn't need it — spurious warnings

// ❌ UHT error: const property
UPROPERTY()
const UObject* ReadOnlyRef;
// ✅ Remove const or remove UPROPERTY
const UObject* ReadOnlyRef;

3. Using bare UPROPERTY() thinking it's needed for all members

// ❌ Unnecessary — adds reflection overhead for no benefit
UPROPERTY()
int32 TempCounter;
// ✅ Skip it — this is local working data
int32 TempCounter;

Only add UPROPERTY() when you actually use one of its features (replication, Blueprint, GC rooting, serialization).
