DMA & Bus Mastering

> [!info] Prerequisites > 04 — CPU Architecture (coming soon) — how the CPU executes instructions and accesses memory. > NVMe & PCIe (coming soon) — the bus that DMA devices use.

Why This Matters

Without DMA, every byte read from an SSD would be copied by the CPU: CPU reads from disk controller → CPU writes to RAM. For a 1 GB/s NVMe drive, that's 1 billion load-store pairs per second — consuming 100% of a CPU core just to move data. DMA (Direct Memory Access) offloads this to dedicated hardware: the DMA engine transfers data directly between devices and RAM, without involving the CPU. The CPU just issues a "copy this block from device A to address X" command and goes back to running game logic. After this note, you'll understand how DMA enables the data rates modern systems demand and why DMA attacks are a security concern.

The Problem DMA Solves

Without DMA (Programmed I/O): `` CPU: while (bytes_remaining > 0) { data = read_from_device(); // CPU reads from disk controller write_to_ram(data); // CPU writes to RAM bytes_remaining--; } // CPU is 100% busy — can't do anything else ` With DMA: ` CPU: DMA_engine->Transfer(device_addr, ram_addr, byte_count); // CPU is free immediately — ~2 microseconds to set up, then free // DMA engine handles the entire transfer // Interrupt fires when done: DMA_engine->OnComplete(); `

How DMA Works — The Three Actors

  1. CPU — Programs the DMA controller with source address, destination address, and byte count
  1. DMA Controller (DMAC) — Specialized hardware that performs the actual memory-to-memory or device-to-memory transfer. Modern systems integrate DMACs into the chipset or each PCIe device
  1. Device — The peripheral (NVMe drive, GPU, network card, audio chip) that wants to move data
The transfer cycle (bus mastering DMA): `
  1. CPU programs DMA controller: "Transfer 4096 bytes from PCIe device 0x3A00 to RAM 0x7FFF0000"
  1. DMA controller requests bus ownership from the memory controller
  1. DMA controller performs the transfer: reads from device, writes to RAM
  1. Each transfer is a burst (typically 64-128 bytes) to minimize bus arbitration overhead
  1. After all bytes transferred, DMA controller sends interrupt to CPU
  1. CPU acknowledges completion and processes the data (e.g., decompresses texture into GPU)
`

DMA Controller Architecture

Traditional (8237-style) — Third-party DMA

A separate chip on the motherboard handles DMA for all devices. The 8237 DMA controller (used in original IBM PC) had 4 channels, each handling one device. Limited to 64KB transfers per operation due to 16-bit address registers. Still present for legacy compatibility but rarely used.

Bus Mastering DMA — First-party DMA

Modern PCIe devices contain their OWN DMA engine. The device itself becomes a "bus master" — it can initiate reads and writes to system RAM without going through a central DMA controller. Each NVMe drive, GPU, and network card has its own DMA engine. ` PCIe Device (bus master) │ ├── DMA Engine ← "Read 4096 bytes from RAM 0x7FFF0000" │ "Write 4096 bytes to RAM 0x80000000" ├── Device Logic ← NVMe controller, GPU command processor, etc. └── MSI-X ← "I'm done!" → CPU interrupt `

DMA and Virtual Memory — The IOMMU

The CPU uses virtual addresses; DMA engines use physical addresses. This creates a problem: how does the DMA engine know the physical address corresponding to the virtual address the program requested? Without IOMMU (legacy):
  • Driver allocates physically contiguous memory (using kmalloc in kernel)
  • Passes the PHYSICAL address to the DMA engine
  • Limitation: need physically contiguous buffers; fragmentation can prevent large allocations
With IOMMU (Intel VT-d / AMD-Vi):
  • IOMMU provides address translation for DMA devices, just like the MMU does for the CPU
  • The DMA engine uses device virtual addresses (IOVA); the IOMMU translates to physical addresses
  • Benefits:
- Can use non-contiguous physical pages (scatter-gather DMA) - Device isolation: a device can only access memory mapped for it (prevents DMA attacks) - 32-bit devices can access memory above 4GB via IOMMU remapping (Double Address Cycle, DAC)

Scatter-Gather DMA

Real-world data isn't always contiguous. A 4MB texture might be split across 16 non-contiguous 256KB pages in physical RAM. Scatter-gather DMA handles this: ` Scatter-Gather List (SGL): ┌──────────────┬───────────────┬──────────┐ │ Entry │ Physical Addr │ Size │ ├──────────────┼───────────────┼──────────┤ │ SG[0] │ 0x7FFF_0000 │ 256 KB │ │ SG[1] │ 0x8000_5000 │ 256 KB │ │ SG[2] │ 0x9000_A000 │ 256 KB │ │ ... │ ... │ ... │ └──────────────┴───────────────┴──────────┘ DMA engine reads SGL and chains transfers: Read 256KB from 0x7FFF_0000 → write to device Read 256KB from 0x8000_5000 → write to device (next in chain) ... ` This is how all modern storage and networking works.

The IOMMU — DMA's Security Guard

DMA engines can read and write ANY physical memory. A malicious PCIe device (or a compromised driver) could DMA into kernel memory, overwriting sys_call_table to redirect read() to attacker code. The IOMMU (Input-Output Memory Management Unit, Intel VT-d / AMD-Vi) prevents this by adding virtual-to-physical address translation for DEVICES: ` Without IOMMU With IOMMU GPU request: "Read KB at phys 0x1000" GPU request: "Read KB at IOVA 0x5000" ↓ ↓ RAM ←── direct access IOMMU: IOVA 0x5000 → phys 0x1000 (any physical address!) IOMMU: IOVA 0x9000 → INVALID (page fault) ↓ RAM ←── only mapped pages ` The IOMMU maintains a page table JUST for devices. The OS programs it: "GPU can access physical pages 0x1000-0x2000 and 0x8000-0x9000, and NOTHING else." Any DMA to an unmapped IOVA triggers an IOMMU fault → kernel receives interrupt → device driver gets an error (or the device is reset).

What the IOMMU Enables

  1. Device isolation: Each PCIe device gets its own IOVA space. GPU can't access NVMe's DMA buffers. A compromised Thunderbolt device can't read system memory.
  1. Scatter-gather without physically contiguous memory: The IOMMU presents a contiguous IOVA range to the device while mapping it to discontiguous physical pages behind the scenes. The device sees a flat buffer; the IOMMU stitches physical pages together.
  1. User-space DMA: VFIO` (Virtual Function I/O) maps device BARs and DMA buffers into user process page tables. DPDK (Data Plane Development Kit) and GPU passthrough use this — a user-space process drives a NIC or GPU with zero kernel involvement per packet/frame.
  1. SR-IOV (Single Root I/O Virtualization): A single physical NIC exposes multiple "virtual functions" — each with its own IOMMU domain. VM #1's virtual NIC can DMA only to VM #1's memory, even though the same physical chip handles all traffic.
// DPDK — user-space networking via IOMMU/VFIO:

void* rx_buffer = rte_pktmbuf_mtod(mbuf, void*);
// NIC DMAs packet directly into rx_buffer — zero copy, zero syscall

### The DMA Attack — Why IOMMU Matters for Thunderbolt

Thunderbolt carries PCIe over a USB-C cable. Plug in a malicious Thunderbolt device and it appears as a PCIe endpoint — capable of initiating DMA reads/writes. Without an IOMMU, the attacker can:

1. DMA-read physical memory → scan for crypto keys, passwords in RAM
2. DMA-write to kernel structures → overwrite `sys_call_table` or page tables
3. Inject code via DMA to a writable+executable page

With IOMMU enabled: the Thunderbolt device is restricted to an IOVA space containing ONLY the buffers the driver explicitly mapped for it. Even if the device is malicious, it can't access anything outside its assigned region.

## DMA in Game Engines

### GPU DMA — DirectStorage
Historically, loading a texture: CPU reads compressed data from SSD (via DMA) → CPU decompresses → CPU copies to GPU (via DMA again). Two DMA transfers + CPU decompression time. DirectStorage (Windows) / RTX IO (NVIDIA) cuts out the middleman:

```
Before:   SSD ──DMA──→ RAM ──CPU decomp──→ RAM ──DMA──→ GPU VRAM
After:    SSD ──DMA──→ GPU decomp──→ GPU VRAM
```

The GPU's DMA engine reads directly from the NVMe drive, and the GPU decompresses the data on its compute units. Near-zero CPU involvement.

### Audio DMA — Circular Buffers

Audio chips use DMA with circular buffers to stream audio continuously:
```
Ring Buffer: [▮▮▮▮▮░░░░░░░░░░░]  ← DMA reads from filled region
           ▲              ▲
        Write ptr     Read ptr (DMA position)
```
The CPU writes new audio data ahead of the DMA read pointer. If the CPU falls behind (write ptr catches read ptr), you get an audible glitch (buffer underrun).

## DMA Attacks — The Security Angle

Because DMA devices bypass the CPU and access physical RAM directly, a malicious PCIe device (e.g., plugged into Thunderbolt port) can read or modify any memory — passwords, encryption keys, kernel code. IOMMU prevents this by restricting each device to ONLY the memory regions explicitly mapped for it. Modern OSes enable IOMMU by default for Thunderbolt devices.

## Two-Way Explanation

### Simple
The CPU is the CEO of a company. Without DMA, the CEO personally carries every box from the loading dock to storage — 1 billion boxes per second for an NVMe drive. DMA hires a forklift operator (DMA engine) — the CEO points at a pallet and says "move these 100 boxes to shelf 42," then goes back to strategy meetings. The forklift operator handles the entire move and taps the CEO on the shoulder (interrupt) when done. The IOMMU is the security guard making sure the forklift doesn't wander into the accounting department's files.

### Technical
DMA controllers perform memory-to-memory and device-to-memory transfers without CPU involvement per byte. Bus mastering DMA devices (PCIe endpoints) contain their own DMA engines and can initiate PCIe Memory Read/Write TLPs (Transaction Layer Packets) directly to system RAM. The IOMMU translates I/O virtual addresses (IOVA) to physical addresses, enabling scatter-gather and device isolation. Transfer size per DMA command is limited by the controller's byte-count register (typically 24-bit for modern engines = 16MB max per descriptor). DMA descriptors are chained via linked lists for arbitrarily large transfers. Cache coherency: DMA engines can be cache-coherent (snoop CPU caches) or require explicit cache flushes (e.g., `clflush` on x86) before DMA reads.
