Syscalls & Kernel

> Why This Matters. Your program runs in a sandbox — it can add numbers and access its own memory, but it cannot touch the filesystem, talk to the network, allocate physical memory, or spawn threads on its own. Every interaction with the outside world requires crossing into the kernel through a system call. Understanding this boundary explains where latency comes from, why batching operations matters, and what actually happens when your program "asks the OS for help." > [!info] Learning Objectives > By the end of this note you will: (1) explain the exact mechanism of a syscall instruction — registers, MSRs, ring transition; (2) distinguish fast-path syscalls (vDSO, getpid cache) from slow-path (I/O); (3) describe how the kernel validates and dispatches syscalls via the syscall table; (4) understand the security mitigations (KPTI, SMEP/SMAP) and their performance cost.

The Hardware Protection Mechanism — Protection Rings

x86-64 CPUs implement protection rings — four privilege levels (Ring 0 through Ring 3). In practice, only two are used:
RingPrivilegeRuns
-----------------------
Ring 0Full hardware accessOS kernel, device drivers
Ring 3RestrictedUserspace applications (your code)
From Ring 3, the CPU physically cannot:
  • Access memory mapped as kernel-only (page table U/S bit blocks it).
  • Execute privileged instructions (lgdt, lidt, mov cr3, hlt, in, out, etc.).
  • Modify page tables directly.
  • Mask interrupts.
Any attempt triggers a General Protection Fault (#GP) — the CPU traps to the kernel, which typically kills the offending process with a SIGSEGV or SIGILL. Analogy: Ring 3 is like a hotel guest room — you control your own space, but you can't access the boiler room, front desk safe, or electrical panel. To get something from those restricted areas, you must ask staff (the kernel) through a formal request (the syscall). The staff verifies your identity and the legitimacy of your request before acting.

The Syscall Instruction — How Ring 3 Crosses to Ring 0

The only controlled way to enter the kernel is through a syscall instruction. On x86-64, that instruction is syscall (Intel and AMD both support it). `` ; x86-64 Linux: sys_write(1, "hello", 5) mov rax, 1 ; Syscall number: 1 = sys_write mov rdi, 1 ; Arg 1: fd = stdout mov rsi, msg ; Arg 2: buffer pointer mov rdx, 5 ; Arg 3: length syscall ; ENTER KERNEL ; ... kernel does the work ... ; Return value in RAX when kernel executes sysret `

What Happens During syscall — A Hardware Trace (Intel x86-64)

The syscall instruction performs this exact sequence on the Intel x86-64 CPU: `
  1. RCX = RIP ; Save return address into RCX (not the stack — syscall doesn't touch RSP)
  1. R11 = RFLAGS ; Save flags register
  1. RIP = IA32_LSTAR ; Load kernel entry point from Model-Specific Register
  1. CS = IA32_STAR[47:32] ; Switch code segment to Ring 0 descriptor
  1. SS = IA32_STAR[47:32] + 8 ; Switch stack segment to Ring 0
  1. RFLAGS = RFLAGS & ~IA32_FMASK ; Clear interrupt-disable and other flags
` The CPU is now running kernel code at Ring 0. The kernel:
  1. Saves remaining registers (pushes them on the kernel stack).
  1. Validates all arguments — critically, every pointer must be in userspace, not kernel memory (otherwise kernel reads could be exploited to leak kernel data).
  1. Performs the requested operation (I/O, memory mapping, process creation, etc.).
  1. Restores registers.
  1. Executes sysret / sysexit:
` RIP = RCX ; Restore return address RFLAGS = R11 ; Restore flags CS/SS = Ring 3 descriptors ; Drop privilege back to Ring 3 ` Execution resumes in userspace at the instruction after syscall, with the return value in RAX (negative values indicate errors: -errno).

Post-Meltdown Syscall Cost — KPTI

The Meltdown vulnerability (2018) revealed that on Intel CPUs (and some ARM), speculative execution could read kernel memory from userspace — even though the access would eventually be blocked by the page table permission check, the speculatively loaded data ended up in cache, where it could be measured via a timing side-channel. The fix: Kernel Page Table Isolation (KPTI). The kernel's memory is now unmapped from userspace page tables. Every syscall must:
  1. Switch CR3 (page table root) from userspace tables to kernel tables.
  1. On sysret: switch CR3 back.
This adds 100–500+ cycles to every syscall. On older CPUs without PCID (Process Context Identifiers), the entire TLB is flushed on each switch — catastrophic for workloads making frequent syscalls. Modern CPUs with PCID tag TLB entries with a process ID, so only kernel entries are flushed; userspace TLB entries survive the round-trip.

Tip
Why engines batch I/O: Every syscall has a floor of ~200–300 cycles of mode-switch overhead. One write() of a 1 MB buffer costs ~300 + copy_time. One million write() calls of 1 byte each costs ~300,000,000 cycles — almost all overhead. This is why bulk operations (render command buffers, memcpy loops, asset streaming) are dramatically faster than naive per-element kernel calls.

vDSO — Syscall-Free Kernel Data Access

The kernel maps two special pages into every process's address space: ` Process Virtual Address Space: ... [vvar] ← Read-only page updated by kernel timer interrupt [vdso] ← Executable page containing __vdso_clock_gettime() code ... ` The vDSO (Virtual Dynamic Shared Object) contains userspace functions that read kernel data from the vvar page without a syscall:
vDSO FunctionSyscall It ReplacesSpeedup
-------------------------------------------
__vdso_clock_gettime()clock_gettime() syscall~15–40× faster
__vdso_gettimeofday()gettimeofday() syscall~15–40× faster
__vdso_time()time() syscall~15× faster
__vdso_getcpu()getcpu() syscall~10× faster

How vDSO Works — Hardware Perspective

The kernel's timer interrupt handler writes the current timestamp into the vvar page. When userspace calls clock_gettime(), glibc detects the vDSO and calls __vdso_clock_gettime() — which reads the timestamp directly from the vvar page in userspace: ` Syscall path (slow): vDSO path (fast): clock_gettime() clock_gettime() → syscall instruction → __vdso_clock_gettime() → Ring 0 switch → read [vvar + offset] ← pure userspace read → kernel reads TSC → compute nanoseconds → compute nanoseconds → return → sysret back to Ring 3 ~20–50 cycles ~300–800 cycles ` No mode switch, no CR3 write, no TLB flush — just a function call + memory read. For game engines calling clock_gettime() thousands of times per frame for profiling and delta-time calculation, vDSO is critical.
Note
Windows equivalent: KUSER_SHARED_DATA — a read-only page at fixed address 0x7FFE0000 (32-bit) containing tick count, time, and system info. GetTickCount() and QueryPerformanceCounter() read this page without a mode switch.

Interrupts — Hardware Events That Demand Attention

An interrupt is a physical electrical signal sent to the CPU's interrupt pin. When it fires:
  1. CPU saves current RIP, RFLAGS, and RSP to the kernel stack
  1. CPU looks up the interrupt number in the IDT (Interrupt Descriptor Table — an array of handler addresses set up at boot)
  1. CPU jumps to the handler (kernel code at ring 0)
  1. Handler processes the event (keyboard press, timer tick, disk I/O complete, page fault)
  1. Returns via iret (interrupt return) — restores RIP/RFLAGS/RSP, returns to ring 3
Types:
  • Hardware interrupts: From devices — keyboard, timer (LAPIC), network card, SSD controller
  • Software interrupts: int 0x80 (legacy 32-bit syscall) or syscall instruction (fast 64-bit)
  • Exceptions: Page fault (#PF), division by zero (#DE), invalid opcode (#UD), general protection fault (#GP)
The IDT entries for exceptions point to handlers that may kill the process (SIGSEGV) or fix the problem and retry (page fault handler allocates a page, then resumes). Why interrupts come before syscalls in this note: A syscall is itself a type of interrupt (a software-interrupt-like mechanism). The syscall instruction reuses the same privilege-level-switching machinery that hardware interrupts use. Understanding interrupts first makes the syscall mechanism obvious — syscall is just a faster, purpose-built version of int 0x80 that skips the full IDT lookup.

Futex — The Fast Userspace Mutex

The futex (Fast Userspace muTEX) is the kernel primitive that enables efficient thread synchronization. It is the foundation beneath pthread_mutex, std::mutex, std::condition_variable, and semaphores on Linux. The key insight: Most mutex operations happen in userspace with no kernel involvement. The kernel is only called when a thread actually needs to block or wake up.

Futex Operation — The Optimistic Fast Path

` Userspace: atomic_compare_exchange(&futex_word, 0, 1) If it was 0 → we got the lock, NO SYSCALL (~20 cycles) If it was 1 → someone holds the lock → call futex(FUTEX_WAIT, &futex_word, 1) > [!note] Learning Path Note > Atomic is explained in detail in Atomics & Memory Ordering (coming soon). This note only covers what is necessary for the current topic. Kernel: Puts the calling thread to sleep on a wait queue. When the lock holder calls futex(FUTEX_WAKE, &futex_word, 1): Moves one waiting thread from the wait queue to the run queue. ` The full lifecycle: ` Lock: 1. atomic_cmpxchg(lock_word, 0, 1) ; Userspace, ~20 cycles 2. If success: done. No kernel involvement. 3. If fail: futex(FUTEX_WAIT, &lock_word, 1) ; Kernel: block thread 4. Kernel checks lock_word still == 1 (racy check under kernel lock) 5. Kernel adds thread to futex wait queue, deschedules it Unlock: 1. atomic_store(lock_word, 0) ; Userspace, ~5 cycles 2. futex(FUTEX_WAKE, &lock_word, 1) ; Kernel: wake one waiter 3. Kernel moves waiter from wait queue to run queue `
Tip
Why this design matters for game engines: In the uncontended case (the common case for well-designed lock usage), a mutex lock/unlock pair costs ~25–30 cycles — purely userspace atomics. The kernel only gets involved on contention. This is why std::mutex can be used in hot paths as long as contention is rare.

## Two-Way Explanation

### Simple

Your program runs in a restricted "user mode" sandbox. To do anything with the outside world — read a file, send network data, allocate memory, create a thread — it must ask the operating system kernel through a system call. The CPU has a special instruction (`syscall`) that switches from user mode to kernel mode, letting the kernel safely do the privileged work. After the kernel finishes, it switches back. This crossing is expensive (hundreds of CPU cycles), so good programs batch their requests. Some clever tricks (vDSO, futex) avoid the crossing entirely for common operations — the kernel puts data directly into the program's memory, and the program reads it without any switch.

### Technical
The `syscall` instruction (x86-64) saves RIP into RCX and RFLAGS into R11, loads the kernel entry point from the LSTAR MSR, and switches CS/SS to Ring 0 descriptors. Post-Meltdown, KPTI requires a CR3 switch on every transition to avoid kernel memory being mapped in userspace page tables, adding 100–500+ cycles. The vDSO avoids this by mapping kernel-updated data pages (`vvar`) and code pages (`vdso`) into every process — functions like `clock_gettime()` execute entirely in userspace. The futex mechanism provides hybrid synchronization: an atomic userspace fast path for the uncontended case, with `FUTEX_WAIT`/`FUTEX_WAKE` syscalls invoked only when a thread must block or be woken.

## Interrupts — Hardware Events That Demand Attention

An interrupt is a physical electrical signal sent to the CPU's interrupt pin. When it fires:

1. CPU saves current RIP, RFLAGS, and RSP to the kernel stack
2. CPU looks up the interrupt number in the **IDT** (Interrupt Descriptor Table — an array of handler addresses set up at boot)
3. CPU jumps to the handler (kernel code at ring 0)
4. Handler processes the event (keyboard press, timer tick, disk I/O complete, page fault)
5. Returns via `iret` (interrupt return) — restores RIP/RFLAGS/RSP, returns to ring 3

**Types:**

  • **Hardware interrupts:** From devices — keyboard, timer (LAPIC), network card, SSD controller


  • **Software interrupts:** `int 0x80` (legacy 32-bit syscall) or `syscall` instruction (fast 64-bit)


  • **Exceptions:** Page fault (#PF), division by zero (#DE), invalid opcode (#UD), general protection fault (#GP)


The IDT entries for exceptions point to handlers that may kill the process (SIGSEGV) or fix the problem and retry (page fault handler allocates a page, then resumes).

## I/O — How the CPU Talks to Devices

Two mechanisms exist for the CPU to communicate with hardware:

### Memory-Mapped I/O (MMIO) — The Modern Standard

Device registers are mapped into the physical address space. The CPU reads/writes to specific physical addresses, and the memory controller routes those accesses to the device instead of RAM.

```c
// GPU command buffer: write to physical address 0xFE000000

volatile uint32_t* gpu_cmd = (uint32_t*)0xFE000000;
*gpu_cmd = DRAW_TRIANGLES;  // GPU starts rendering

```

### Port-Mapped I/O (PMIO) — Legacy x86

Uses special `in`/`out` instructions to access a separate 16-bit I/O address space. Rare in modern systems — mostly for legacy devices (PS/2 keyboard, legacy VGA).

Modern systems use MMIO almost exclusively. The PCIe configuration space, GPU command buffers, NVMe submission queues — all accessed via memory-mapped addresses.

## Common Pitfalls

1. **Assuming syscalls are free:** A `getpid()` call may seem cheap, but every syscall costs a ring transition (100–500 cycles) plus potential KPTI TLB flushes. Calling `getpid()` in a loop instead of caching it once can waste microseconds per iteration.

2. **Forgetting that syscalls can fail:** `write()` can return fewer bytes than requested (partial write). Always check the return value and retry if necessary. `close()` can also fail (NFS over a disconnected link) — many codebases ignore this.

3. **Misunderstanding vDSO:** `gettimeofday()` via vDSO is ~25 cycles — faster than a regular function call because it's mapped kernel code in userspace. But this only works for read-only syscalls that don't change kernel state. Don't expect `write()` to ever get a vDSO path.

  1. **Assuming syscalls are idempotent:** `close(fd)` followed by another `close(fd)` may close the fd that was reassigned to another thread in between — a classic TOCTOU race in signal handlers.
