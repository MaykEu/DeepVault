Testing & Quality

> [!info] Prerequisites: RAII & Rule of Five (coming soon) (test fixtures are RAII), Exceptions & Error Handling (coming soon) (testing exception safety). No prior testing framework experience assumed. > [!tip] Why This Matters > You've learned SOLID, patterns, templates, and concurrency. None of it matters if your code is wrong. Testing is not a post-development chore — it's the feedback loop that tells you whether your design works. A game shipped with a memory corruption bug loses players. A test suite that catches that bug in 2 seconds (instead of 2 weeks of player reports) pays for itself a thousand times over. This note teaches the C++ testing toolkit: Catch2 for unit tests, sanitizers for runtime bugs, and TDD as a design discipline.

Why Test in C++?

C++ gives you power and speed. It also gives you:
  • Undefined behavior (use-after-free, buffer overflow, data races)
  • Silent corruption (uninitialized variables, signed overflow, strict aliasing violations)
  • Platform-dependent behavior (sizeof, alignment, endianness)
The compiler won't catch these. Neither will code review (consistently). Only automated tests + sanitizers catch them reliably.

Catch2 — Modern C++ Unit Testing

Catch2 is the most popular C++ test framework. Single header, no preprocessor magic, expressive syntax.

Basic Test

#define CATCH_CONFIG_MAIN

#include <catch2/catch.hpp>

int Add(int a, int b) { return a + b; }

TEST_CASE("Addition works", "[math]") {
 REQUIRE(Add(2, 2) == 4);
 REQUIRE(Add(-1, 1) == 0);
 REQUIRE(Add(0, 0) == 0);
}
```

`REQUIRE` is a hard assertion — test stops on failure. `CHECK` is a soft assertion — test continues, reports all failures.

### Sections — Isolated Sub-Tests

```cpp
TEST_CASE("Vector operations", "[vector]") {
 std::vector<int> v;
 
 SECTION("Empty vector") {
     REQUIRE(v.empty());
     REQUIRE(v.size() == 0);
 }
 
 SECTION("After push_back") {
     v.push_back(42);
     REQUIRE(v.size() == 1);
     REQUIRE(v[0] == 42);
 }
 
 SECTION("After multiple push_backs") {
     v.push_back(1);
     v.push_back(2);
     v.push_back(3);
     REQUIRE(v.size() == 3);
 }
}
// Each SECTION runs with a FRESH 'v' — they don't interfere

```

Sections are NOT sequential — each section runs from the top of the TEST_CASE, re-executing the shared setup. Think of them as forking the test at each SECTION boundary.

### Fixtures — Shared Setup/Teardown

```cpp
class DatabaseFixture {
protected:
 Database db;
 DatabaseFixture() : db(":memory:") { db.Initialize(); } // setup

 ~DatabaseFixture() { db.Close(); }                       // teardown

};

TEST_CASE_METHOD(DatabaseFixture, "Insert and query", "[db]") {
 REQUIRE(db.Insert("key", "value"));
 REQUIRE(db.Query("key") == "value");
}
// Fixture constructor runs before each TEST_CASE_METHOD, destructor after

```

### When to Use Each

| Context | Use | Because |
|---------|-----|---------|
| Independent tests, no shared state | `TEST_CASE` | Simplest, fastest |
| Tests with multiple scenarios from same setup | `SECTION` | Reuses setup, isolates scenarios |
| Tests that need resource setup/teardown | `TEST_CASE_METHOD` | RAII-like lifecycle |
| Parametric tests (same logic, different data) | Catch2 generators or `TEST_CASE` loop | Avoids copy-paste |

## What to Test — The Testing Pyramid

```
  ┌──────────┐
  │   E2E    │  Few: full game loop, load level, complete match
  ├──────────┤
  │Integration│  Some: multiple systems interacting (physics + rendering)
  ├──────────┤
  │   Unit    │  Many: individual functions, classes, algorithms
  └──────────┘
```

**Unit tests:** Test ONE thing in isolation. `Vector3::Normalize()` returns unit vector. `Arena::Alloc()` returns non-overlapping memory. Fast (<1ms), run on every compile.

**Integration tests:** Test interaction between units. `PhysicsSystem` applies forces → `RenderingSystem` sees updated transforms. Fewer, run on commit.

**E2E tests:** Test the whole program. Load level, play 60 frames, assert no crash. Very few, run on CI.

### The Golden Rules of Unit Tests

1. **Test behavior, not implementation.** Don't test that `m_count` is 5 — test that after 5 inserts, `size()` returns 5.

  1. **One logical assertion per test.** `TEST_CASE("Empty vector has size 0 and is empty")` — two assertions, ONE concept.


  1. **Tests must be deterministic.** No `rand()`, no `std::chrono::now()`, no thread scheduling dependency. Use fixed seeds and mocked time.


  1. **Tests must be fast.** A test suite that takes 10 minutes doesn't get run. Aim for <1 second total unit test time.

## Test-Driven Development — Tests Before Code

```
RED → GREEN → REFACTOR
│      │        │
│      │        └─ Clean up code while tests pass
│      └─ Write MINIMAL code to pass
└─ Write a FAILING test first
```

### TDD Workflow for a Vector3 Class

```cpp
// STEP 1 — RED: write the test first (it won't compile — no Vector3 yet)

TEST_CASE("Vector3 length computes correctly", "[math]") {
 Vector3 v{3.0f, 4.0f, 0.0f};
 REQUIRE(v.Length() == 5.0f);
}

// STEP 2 — GREEN: write MINIMAL code to pass

struct Vector3 {
 float x, y, z;
 float Length() const { return std::sqrt(x*x + y*y + z*z); }
};

// STEP 3 — REFACTOR: test still passes, improve code

struct Vector3 {
 float x, y, z;
 `[[nodiscard]]` float Length() const { return std::sqrt(x*x + y*y + z*z); }
 `[[nodiscard]]` float LengthSquared() const { return x*x + y*y + z*z; }
};
```

**Why TDD works for game code:** Game features have clear, testable behavior: "player takes 10 damage at 5 health → health becomes 0, player dies." Write that test, then implement. You now have a regression test forever.

## Sanitizers — The Compiler As Detective

Sanitizers instrument your compiled code to detect bugs at runtime. Zero false positives (by design). See [[../06 — Build & Debug Tools|Build & Debug Tools]] for setup. Here's the testing integration:

### AddressSanitizer (ASan) — Memory Errors

```bash
g++ -fsanitize=address -g -O1 -o test test.cpp
./test
```

Catches: use-after-free, heap/stack buffer overflow, double-free, memory leaks (with `-fsanitize=leak`).

```cpp
// ASan catches this:
int* p = new int(42);
delete p;
*p = 10; // ⚡ ASan: heap-use-after-free at line X
```

### UndefinedBehaviorSanitizer (UBSan) — Logic Errors

```bash
g++ -fsanitize=undefined -o test test.cpp
```

Catches: signed integer overflow, null pointer dereference, misaligned access, division by zero, out-of-bounds enum values, invalid `this` in member function.

```cpp
int x = INT_MAX;
x += 1; // ⚡ UBSan: signed integer overflow
```

### ThreadSanitizer (TSan) — Data Races

```bash
g++ -fsanitize=thread -o test test.cpp
```

Catches: data races (unsynchronized concurrent access where at least one is a write).

**The testing pyramid with sanitizers:**

```
Every commit:     Unit tests + ASan + UBSan  (fast, catch most bugs)
Every PR:         Integration tests + TSan   (slower, catch threading bugs)
Nightly:          E2E tests + full sanitizer matrix (slow, catch rare issues)
```

## Structuring a C++ Test Suite

```
project/
├── src/           # production code
├── include/       # headers
├── test/          # test code
│   ├── unit/      # unit tests (mirror src/ structure)
│   ├── integration/
│   └── CMakeLists.txt
└── CMakeLists.txt
```

### CMake Integration

```cmake
# Fetch Catch2
include(FetchContent)
FetchContent_Declare(Catch2 GIT_REPOSITORY https://github.com/catchorg/Catch2.git
                        GIT_TAG v3.4.0)
FetchContent_MakeAvailable(Catch2)

# Test executable
add_executable(vector_tests test/unit/vector_tests.cpp)
target_link_libraries(vector_tests PRIVATE Catch2::Catch2WithMain my_library)

# Register with CTest
include(CTest)
add_test(NAME vector_tests COMMAND vector_tests)
```

Run with: `cd build && ctest --output-on-failure`

## Two-Way Explanation

**Beginner:** Testing is writing code that verifies your other code works. Catch2 lets you write `REQUIRE(Add(2,2) == 4)` — if it's wrong, the test fails and tells you exactly what went wrong. TDD means writing the test BEFORE the code: first you write a failing test, then you write just enough code to make it pass, then you clean up. Sanitizers are compiler flags (`-fsanitize=address`) that add runtime checks — they catch memory bugs, undefined behavior, and data races that would otherwise silently corrupt your game.

**Experienced:** Catch2 provides a behavior-driven testing DSL with SECTION-based test isolation (each SECTION re-executes shared setup, enabling independent scenarios without fixture duplication). The testing pyramid guides investment: many fast unit tests at the base, fewer integration tests, very few E2E tests. TDD (Red→Green→Refactor) is a design discipline: tests are an executable specification that survives refactoring. The sanitizer suite (ASan, UBSan, TSan) should run on every CI pipeline — they're deterministic, zero-false-positive detectors for the three most common C++ bug categories (memory, UB, concurrency). CTest + CMake's `add_test()` integrate tests into the build system; `ctest --output-on-failure` provides CI-friendly output. Property-based testing (not covered in detail) generates random inputs and verifies invariants — complementary to example-based unit tests.

## Exercises

1. **Write tests for your Vector class:** Create a `Vec3` class. Write Catch2 tests for: construction, addition, normalization (including zero-vector edge case), dot product, cross product. Run with `-fsanitize=address,undefined`.

2. **TDD a Ring Buffer:** Write the test first: `RingBuffer<int> buf(3); buf.Push(1); buf.Push(2); REQUIRE(buf.Pop() == 1);`. Implement the minimal code. Add a test for buffer-full behavior. Implement. Refactor. Run ASan on all tests.

3. **ASan catching bugs:** Write a function that allocates an array, returns a pointer to it, and the caller uses it after the function returns (use-after-return). Compile with and without ASan. Does ASan catch it? What if you use `-fsanitize=address` with `ASAN_OPTIONS=detect_stack_use_after_return=1`?

4. **TSan data race:** Write a counter incremented by 2 threads without synchronization. Write a Catch2 test that runs the increment loop. Compile with TSan. Does the test always fail? Does TSan always report the race?

5. **Testing pyramid design:** Your game has `Player::TakeDamage()`, `Enemy::UpdateAI()`, and a full `GameLoop::Tick()`. Propose: which level (unit/integration/E2E) for each? What would each test verify? What sanitizers would you use for each level?
