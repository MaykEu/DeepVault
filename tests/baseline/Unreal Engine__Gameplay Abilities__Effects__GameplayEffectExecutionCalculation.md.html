GameplayEffectExecutionCalculation

Overview

An ExecutionCalculation gives you complete control over what happens when a Gameplay Effect executes. Unlike an MMC which computes a single modifier magnitude, an EEC can:
  • Emit any number of modifiers affecting different attributes
  • Apply conditional Gameplay Effects based on runtime logic
  • Access both the source and target AbilitySystemComponents
  • Iterate over every qualified modifier affecting captured attributes
  • Control GameplayCue firing and stack count handling
The cost is complexity — you write all the math yourself, no Coefficient/PreMultiply/PostMultiply pipeline. If you need one modifier output with simple math, use an MMC. If you need multiple outputs, conditional branching, or direct ASC access, use an EEC. > [!info] Source > Engine/Plugins/Runtime/GameplayAbilities/Source/GameplayAbilities/Public/GameplayEffectExecutionCalculation.h

Class Hierarchy

`` UObject └── UGameplayEffectCalculation (GameplayEffectCalculation.h) └── UGameplayModMagnitudeCalculation (MMC) └── UGameplayEffectExecutionCalculation (EEC — THIS CLASS) ` Both MMC and EEC share the same base — RelevantAttributesToCapture and GetAttributeCaptureDefinitions()`. The base class is identical; the differences are in what each subclass exposes.

The Execute Function

// GameplayEffectExecutionCalculation.h:310

UFUNCTION(BlueprintNativeEvent, Category="Calculation")
UE_API void Execute(const FGameplayEffectCustomExecutionParameters& ExecutionParams,
                  FGameplayEffectCustomExecutionOutput& OutExecutionOutput) const;
```

This is the only function you **must** override. In C++:

```cpp
virtual void Execute_Implementation(
 const FGameplayEffectCustomExecutionParameters& ExecutionParams,
 FGameplayEffectCustomExecutionOutput& OutExecutionOutput) const override;
```

**Note:** Like MMC's `CalculateBaseMagnitude`, the `_Implementation` suffix is mandatory because this is a `BlueprintNativeEvent`.

## FGameplayEffectCustomExecutionParameters — What You Can Read

This struct is your window into the execution context. Passed by const reference — you can read but not modify through it (except through `GetOwningSpecForPreExecuteMod`).

### Core Access

| Function | Returns | What it gives you |
|---|---|---|
| `GetOwningSpec()` | `const FGameplayEffectSpec&` | The GE spec being executed |
| `GetOwningSpecForPreExecuteMod()` | `FGameplayEffectSpec*` | Non-const spec — modify BEFORE execution |
| `GetTargetAbilitySystemComponent()` | `UAbilitySystemComponent*` | The ASC the GE is applied to |
| `GetSourceAbilitySystemComponent()` | `UAbilitySystemComponent*` | The ASC that applied the GE (can be null!) |
| `GetPassedInTags()` | `const FGameplayTagContainer&` | Tags from the GE's `PassedInTags` config |
| `GetPredictionKey()` | `FPredictionKey` | The prediction key (valid if predicted) |
| `GetIgnoreHandles()` | `TArray<FActiveGameplayEffectHandle>` | GEs to ignore during evaluation |

### Attribute Capture Methods

| Function | Purpose |
|---|---|
| `AttemptCalculateCapturedAttributeMagnitude(CaptureDef, EvalParams, OUT Magnitude)` | Get current value of a captured attribute |
| `AttemptCalculateCapturedAttributeMagnitudeWithBase(CaptureDef, EvalParams, BaseValue, OUT Magnitude)` | Same, starting from a custom base |
| `AttemptCalculateCapturedAttributeBaseValue(CaptureDef, OUT BaseValue)` | Get the base value only |
| `AttemptCalculateCapturedAttributeBonusMagnitude(CaptureDef, EvalParams, OUT Bonus)` | Get bonus magnitude only |
| `AttemptGetCapturedAttributeAggregatorSnapshot(CaptureDef, OUT Aggregator)` | Snapshot the entire aggregator |
| `AttemptGatherAttributeMods(CaptureDef, EvalParams, OUT ModMap)` | Get all qualified modifiers affecting the attribute |
| `ForEachQualifiedAttributeMod(CaptureDef, EvalParams, Func)` | Iterate every qualified modifier with a callback |

### Transient Aggregator Methods

These let you work with scoped modifier "temporary variables" — see the Scoped Modifiers section below.

| Function | Purpose |
|---|---|
| `AttemptCalculateTransientAggregatorMagnitude(Tag, EvalParams, OUT Magnitude)` | Read a transient aggregator's value |
| `AttemptCalculateTransientAggregatorBaseValue(Tag, OUT BaseValue)` | Base value only |
| `AttemptCalculateTransientAggregatorBonusMagnitude(Tag, EvalParams, OUT Bonus)` | Bonus magnitude only |

### FAggregatorEvaluateParameters

Same as in the MMC system. Controls which modifiers count when evaluating captured attributes:

```cpp
FAggregatorEvaluateParameters EvalParams;
EvalParams.SourceTags = ExecutionParams.GetOwningSpec().CapturedSourceTags.GetAggregatedTags();
EvalParams.TargetTags = ExecutionParams.GetOwningSpec().CapturedTargetTags.GetAggregatedTags();
```

## FGameplayEffectCustomExecutionOutput — What You Can Write

This is an OUT parameter. Everything you emit goes through this struct.

### Emitting Modifiers

```cpp
// Add a single modifier
OutExecutionOutput.AddOutputModifier(
 FGameplayModifierEvaluatedData(MyAttributeProperty, EGameplayModOp::Additive, CalculatedDamage));
```

| `FGameplayModifierEvaluatedData` field | Type | Description |
|---|---|---|
| `Attribute` | `FGameplayAttribute` | The FProperty for the attribute |
| `ModifierOp` | `EGameplayModOp::Type` | `Additive`, `Multiplicitive`, `Division`, `Override` |
| `Magnitude` | `float` | The magnitude to apply |
| `Handle` | `FActiveGameplayEffectHandle` | Optional — if set, only modifies that specific GE's contribution |

#### Reading Output Modifiers

After execution, the system reads your modifiers via:
```cpp
const TArray<FGameplayModifierEvaluatedData>& GetOutputModifiers() const;      // const access

void GetOutputModifiers(OUT TArray<FGameplayModifierEvaluatedData>& Out) const;  // copy-out

TArray<FGameplayModifierEvaluatedData>& GetOutputModifiersRef();                 // direct ref (avoid copy)

```
`GetOutputModifiersRef()` is used internally by the engine at `GameplayEffect.cpp:3155` to iterate your output — it avoids making a copy.
| `Handle` | `FActiveGameplayEffectHandle` | Optional — if set, only modifies that specific GE's contribution |

The engine iterates your output modifiers and calls `InternalExecuteMod` for each one (line 3163 in `GameplayEffect.cpp`).

### Automatic Stack Count Scaling

By default, each output modifier is multiplied by the GE's stack count:

```cpp
// GameplayEffect.cpp:3161

if (bApplyStackCountToEmittedMods && SpecStackCount > 1)
{
 CurExecMod.Magnitude = GameplayEffectUtilities::ComputeStackedModifierMagnitude(
     CurExecMod.Magnitude, SpecStackCount, CurExecMod.ModifierOp);
}
```

If you've already accounted for stack count in your math, call:
```cpp
OutExecutionOutput.MarkStackCountHandledManually();
```
This suppresses the automatic stack scaling.

### Conditional Gameplay Effects

```cpp
// By default, conditional GEs from the GE's ExecutionDefinition fire automatically.
// Mark them NOT to fire if the execution determines they shouldn't:

if (bPostureNotBroken)
{
 // Don't fire unconditional effects

 // (by NOT calling MarkConditionalGameplayEffectsToTrigger, they are suppressed)

 // But the GE's ConditionalGameplayEffects ALWAYS fire by default.

 // To stop them: simply don't call MarkConditionalGameplayEffectsToTrigger,

 // and the system checks ShouldTriggerConditionalGameplayEffects() which defaults to false.

}
```

Wait — let me clarify the actual source behavior (line 3285):

```cpp
bRunConditionalEffects = ExecutionOutput.ShouldTriggerConditionalGameplayEffects();
```

`ShouldTriggerConditionalGameplayEffects()` checks `bTriggerConditionalGameplayEffects` which is `false` by default. If the execution doesn't explicitly call `MarkConditionalGameplayEffectsToTrigger()`, conditional GEs from the execution definition are **NOT** applied.

This is the opposite of what you might expect — **conditional GEs are opt-in**. You must call:
```cpp
OutExecutionOutput.MarkConditionalGameplayEffectsToTrigger();
```

### Controlling GameplayCues

```cpp
// Prevent automatic GameplayCue execution (you handle it manually)
OutExecutionOutput.MarkGameplayCuesHandledManually();
```

If you call this, the engine skips its automatic GameplayCue invocation (`InvokeGameplayCueExecuted_FromSpec` at line 3356). You're responsible for invoking cues yourself.

## Attribute Captures

The capture system is **identical to MMC** — see [[Core Mechanics/Attribute Capture System]] for the full details on capture definitions, the spec container, `FindCaptureSpecByDefinition`, and snapshot vs live timing. Use the same setup in your constructor:

```cpp
// Header

DECLARE_ATTRIBUTE_CAPTUREDEF(Health);
DECLARE_ATTRIBUTE_CAPTUREDEF(Strength);

// Constructor

DEFINE_ATTRIBUTE_CAPTUREDEF(UMyAttributeSet, Health, Target, false);
DEFINE_ATTRIBUTE_CAPTUREDEF(UMyAttributeSet, Strength, Source, false);
RelevantAttributesToCapture.Add(HealthDef);
RelevantAttributesToCapture.Add(StrengthDef);
```

[!note]
In an EEC, the macros are especially useful because they give you the `FProperty*` (e.g. `HealthProperty`), which you use when constructing `FGameplayModifierEvaluatedData` for output.

## Emitting Output Modifiers — The Real Work

```cpp
void UMyDamageExec::Execute_Implementation(
 const FGameplayEffectCustomExecutionParameters& ExecParams,
 FGameplayEffectCustomExecutionOutput& OutExecOutput) const
{
 // 1. Set up evaluation parameters

 FAggregatorEvaluateParameters EvalParams;
 const FGameplayEffectSpec& Spec = ExecParams.GetOwningSpec();
 EvalParams.SourceTags = Spec.CapturedSourceTags.GetAggregatedTags();
 EvalParams.TargetTags = Spec.CapturedTargetTags.GetAggregatedTags();

 // 2. Read captured attributes

 float AttackPower = 0.f;
 ExecParams.AttemptCalculateCapturedAttributeMagnitude(AttackPowerDef, EvalParams, AttackPower);

 float Defense = 0.f;
 ExecParams.AttemptCalculateCapturedAttributeMagnitude(DefenseDef, EvalParams, Defense);

 // 3. Calculate

 float Damage = FMath::Max(1.f, AttackPower * 2.0f - Defense * 0.5f);
 float Lifesteal = Damage * 0.3f;

 // 4. Emit output modifiers

 OutExecOutput.AddOutputModifier(
     FGameplayModifierEvaluatedData(HealthProperty, EGameplayModOp::Additive, -Damage));

 OutExecOutput.AddOutputModifier(
     FGameplayModifierEvaluatedData(ManaProperty, EGameplayModOp::Additive, Lifesteal));

 // Optional: fire conditional GEs if the execution warrants it

 OutExecOutput.MarkConditionalGameplayEffectsToTrigger();
}
```

## The Execution Flow — When Your EEC Runs

From `GameplayEffect.cpp` — the execution pipeline in `ExecuteActiveEffectsFrom`:

```
ExecuteActiveEffectsFrom()
│
├─ 1. Calculate modifier magnitudes (regular modifiers + MMC)
│
├─ 2. Execute regular modifiers via InternalExecuteMod
│
├─ 3. For each ExecutionDefinition:
│     ├─ Create FGameplayEffectCustomExecutionParameters
│     │    (Spec, ScopedMods, TargetASC, PassedInTags, PredictionKey)
│     ├─ Create FGameplayEffectCustomExecutionOutput (empty)
│     ├─ Call ExecCDO->Execute(Params, Output) ← YOUR CODE RUNS HERE
│     ├─ Check ShouldTriggerConditionalGameplayEffects()
│     ├─ Iterate output modifiers, apply stack scaling, call InternalExecuteMod
│     └─ Check AreGameplayCuesHandledManually()
│
├─ 4. Apply conditional GEs (if any were triggered)
│
├─ 5. Invoke gameplay cues (unless handled manually)
│
└─ 6. Notify GE components (OnExecuted)
```

**When EEC runs:**

  • **Instant GE**: During `ExecuteGameplayEffect` → `ExecuteActiveEffectsFrom`


  • **Periodic tick**: During `InternalExecutePeriodicGameplayEffect` → `ExecuteActiveEffectsFrom`


  • **Duration/Infinite**: EEC does NOT fire. Only Instant and Periodic GEs trigger executions.


The EEC runs INSIDE `ExecuteActiveEffectsFrom`, **after** regular modifiers have been applied and **before** GameplayCues and conditional effects.

## Scoped Modifiers & Transient Aggregators

The full execution flow — including when EEC runs, how stack scaling works, and how conditional GEs are applied — is covered in [[Core Mechanics/GE Execution Flow]].

### What Scoped Modifiers Do

The `CalculationModifiers` array on `FGameplayEffectExecutionDefinition` applies modifiers **during** the execution — before you read captured attributes and before your Execute function's output modifiers are applied.

This lets the data designer tune the context your EEC sees:

```
GE_Attack:
├── Executions[0]:
│   ├── CalculationClass: UMyDamageExec
│   ├── CalculationModifiers[0]:
│   │   Attribute: EnemyArmor
│   │   ModifierOp: Additive
│   │   Magnitude: -50  (armor piercing = reduces enemy armor by 50)
│   │
│   │   → When EEC reads EnemyArmor, it sees (CurrentArmor - 50)
│   │   → Scoped modifier is applied "in-place" before EEC runs
│   │   → The actual EnemyArmor on the target is NOT modified — scoped only
```

Scoped modifiers create a temporary override of the captured attribute inside the execution context. They don't persist.

### Transient Aggregators

A special type of scoped modifier that doesn't back onto any real attribute. It's a **temporary numeric variable** scoped to this execution:

```cpp
// GE asset config:

// CalculationModifiers[0]:

//   TransientAggregatorIdentifier: "Temp.DamageMultiplier"

//   ModifierOp: Additive

//   Magnitude: 1.5 (data-defined multiplier)

// In your EEC:

float Multiplier = 0.f;
ExecParams.AttemptCalculateTransientAggregatorMagnitude(
 FGameplayTag::RequestGameplayTag("Temp.DamageMultiplier"),
 EvalParams, Multiplier);
// Multiplier is 1.5 — passed through the scoped modifier system

```

Transient aggregators must be declared in `ValidTransientAggregatorIdentifiers` (Editor-only list) for the GE editor to show them.

### bRequiresPassedInTags

```cpp
UPROPERTY(EditDefaultsOnly, BlueprintReadOnly, Category = Attributes)
bool bRequiresPassedInTags;

UE_API bool DoesRequirePassedInTags() const;
```

Set `bRequiresPassedInTags = true` in your EEC constructor if your `Execute` function uses the `PassedInTags` from the GE's ExecutionDefinition. The editor can use this to validate asset configurations.

---

### InvalidScopedModifierAttributes

Some attributes you capture for internal calculation but don't want exposed as tweakable scoped modifiers. Add them to `InvalidScopedModifierAttributes`:

```cpp
// In the EEC's header/defaults:

// RelevantAttributesToCapture: [Health, MaxHealth, Strength]

// InvalidScopedModifierAttributes: [MaxHealth]  ← not exposed to scoped modifiers

```

The editor filters these out from the scoped modifier dropdown.

## Conditional Gameplay Effects

Configured on the GE's `FGameplayEffectExecutionDefinition` — these are GEs that fire after the EEC runs, IF the execution opts in:

```
GE_Attack:
├── Executions[0]:
│   ├── CalculationClass: UMyDamageExec
│   └── ConditionalGameplayEffects[0]:
│       ├── EffectClass: GE_Bleed
│       └── RequiredSourceTags: [State.BleedingWeapon]
```

In your EEC:
```cpp
void UMyDamageExec::Execute_Implementation(...) const
{
 // ... calculate damage, emit modifiers ...

 // Opt-in: fire the conditional GEs defined on this execution
 OutExecOutput.MarkConditionalGameplayEffectsToTrigger();
}
```

The conditional GE's `CanApply(SourceTags, SourceLevel)` is checked. If `RequiredSourceTags` is empty, the GE always applies (when triggered). If tags are set, the source must have ALL of them.

[!warning]
Conditional GEs are **opt-in** — the output's `bTriggerConditionalGameplayEffects` defaults to `false`. Calling `MarkConditionalGameplayEffectsToTrigger()` is required.

## Full Template

```cpp
// MyDamageExec.h
#pragma once

#include "CoreMinimal.h"
#include "GameplayEffectExecutionCalculation.h"
#include "MyDamageExec.generated.h"

UCLASS()
class UMyDamageExec : public UGameplayEffectExecutionCalculation
{
 GENERATED_BODY()

public:
 UMyDamageExec();

 virtual void Execute_Implementation(
     const FGameplayEffectCustomExecutionParameters& ExecParams,
     FGameplayEffectCustomExecutionOutput& OutExecOutput) const override;

protected:
 DECLARE_ATTRIBUTE_CAPTUREDEF(AttackPower);
 DECLARE_ATTRIBUTE_CAPTUREDEF(Defense);
 DECLARE_ATTRIBUTE_CAPTUREDEF(Health);
};
```

```cpp
// MyDamageExec.cpp
#include "MyDamageExec.h"
#include "MyAttributeSet.h"

UMyDamageExec::UMyDamageExec()
{
 DEFINE_ATTRIBUTE_CAPTUREDEF(UMyAttributeSet, AttackPower, Source, false);
 DEFINE_ATTRIBUTE_CAPTUREDEF(UMyAttributeSet, Defense, Target, false);
 DEFINE_ATTRIBUTE_CAPTUREDEF(UMyAttributeSet, Health, Target, false);

 RelevantAttributesToCapture.Add(AttackPowerDef);
 RelevantAttributesToCapture.Add(DefenseDef);
 RelevantAttributesToCapture.Add(HealthDef);
}

void UMyDamageExec::Execute_Implementation(
 const FGameplayEffectCustomExecutionParameters& ExecParams,
 FGameplayEffectCustomExecutionOutput& OutExecOutput) const
{
 // 1. Eval params
 FAggregatorEvaluateParameters EvalParams;
 const FGameplayEffectSpec& Spec = ExecParams.GetOwningSpec();
 EvalParams.SourceTags = Spec.CapturedSourceTags.GetAggregatedTags();
 EvalParams.TargetTags = Spec.CapturedTargetTags.GetAggregatedTags();

 // 2. Read capturess
 float Attack = 0.f, Defense = 0.f;
 ExecParams.AttemptCalculateCapturedAttributeMagnitude(AttackPowerDef, EvalParams, Attack);
 ExecParams.AttemptCalculateCapturedAttributeMagnitude(DefenseDef, EvalParams, Defense);

 // 3. Formula
 float Damage = FMath::Max(1.f, Attack * 2.0f - Defense * 0.5f);

 // 4. Emit modifiers
 OutExecOutput.AddOutputModifier(
     FGameplayModifierEvaluatedData(HealthProperty, EGameplayModOp::Additive, -Damage));

 // 5. Optionally fire conditional GEs
 OutExecOutput.MarkConditionalGameplayEffectsToTrigger();
}
```

## EEC vs MMC — Decision Guide

| Use MMC | Use EEC |
|---|---|
| ONE modifier output | TWO OR MORE modifier outputs |
| Simple formula → single result | Need to apply conditional GEs based on result |
| Want Coefficient/PreMultiply/PostMultiply pipeline | Want full manual control over every modifier |
| Don't need Source ASC access | Need Source ASC (e.g., for actor info, abilities) |
| Blueprint-friendly (simpler set up) | Need `ForEachQualifiedAttributeMod` iteration |
| Posture damage, heal amount, buff | Life steal, execute, explosion, parry, combo system |

## Networking & Prediction

EECs are **never executed on the client** for predicted effects. The `bTreatAsInfiniteDuration` mechanism (which handles predicted instant GEs) skips the `ExecuteGameplayEffect` call entirely (line 1148-1162 in `AbilitySystemComponent.cpp`), which means EEC's `Execute` runs on the server only.

For periodic effects, periodic ticks only execute on the server (line 1022-1031 blocks client-side periodic ticks).

**What this means:**

  • Any logic inside your EEC's `Execute` is server-authoritative only


  • Output modifiers from the EEC are replicated through the normal attribute system


  • If you need client-side visual feedback, use GameplayCues (not EEC logic)


  • Conditional GEs triggered by the EEC are applied server-side and replicated


See [[Prediction & Networking]] for the full prediction system.

## Common Mistakes

### 1. Forgetting the `_Implementation` suffix

```cpp
// ❌ Won't override

void Execute(const FGameplayEffectCustomExecutionParameters&, ...) const;

// ✅ Correct

void Execute_Implementation(const FGameplayEffectCustomExecutionParameters&, ...) const override;
```

### 2. Not calling `MarkConditionalGameplayEffectsToTrigger()`

Conditional GEs are opt-in. If you forget this call, none of your conditional effects fire.

### 3. Double-counting stack count

By default, each output modifier is multiplied by the GE's stack count. If you've already multiplied by stack count in your math, call `MarkStackCountHandledManually()`.

### 4. Reading captured attributes without FAggregatorEvaluateParameters

Without proper SourceTags/TargetTags, the attribute evaluation skips tag filtering and returns ALL modifiers — potentially overcounting.

### 5. Using EEC when MMC would suffice

If you only need ONE modifier output, an MMC is simpler, gives you the Coefficient pipeline, and is Blueprint-friendlier. Don't use EEC for single-modifier formulas.

### 6. Assuming EEC runs for Duration/Infinite effects
Duration and Infinite GEs do NOT execute EECs. Only Instant and Periodic effects trigger executions. Even if you add an Execution to a Duration GE, it won't run unless the GE's `DurationPolicy` is Instant and `Period` is set.

### 7. Capturing the wrong attribute direction
Using `EGameplayEffectAttributeCaptureSource::Source` when you mean `Target` is a common source of wrong values. For damage: attacker's stats are `Source`, defender's stats are `Target`.

### 8. Not building the output modifier with the correct property
```cpp
// ❌ Using the UPROPERTY name instead of the FProperty*
FGameplayModifierEvaluatedData("Health", ...);  // Wrong — won't compile properly

// ✅ Using the macro-generated property

FGameplayModifierEvaluatedData(HealthProperty, EGameplayModOp::Additive, -Damage);
```
