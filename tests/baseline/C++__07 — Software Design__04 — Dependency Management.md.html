Dependency Management

> [!info] Prerequisites: Preprocessor & Macros (coming soon), From Source to Running (coming soon) — the compile/link pipeline. Inheritance & Virtual Functions (coming soon). > [!tip] Why This Matters > Change one line in a header and your entire project recompiles. Add a member to a class and every translation unit that includes it must be rebuilt. In a game engine with 5,000+ .cpp files, a single bad header dependency can turn a 5-second incremental build into a 5-minute wait. This note teaches you how to structure code so that changes ripple as little as possible — measured in seconds of build time and dollars of developer frustration.

The Physics of Build Time

Every #include is a copy-paste. The preprocessor literally inserts the entire header file at the #include site. If Player.h is 2,000 lines and 500 .cpp files #include it, the compiler processes 1,000,000 lines of code before it sees your actual logic. Compile time = (header size × include count) + (own code). Minimize the first term.

Self-Sufficient Headers

> Every header file should compile in isolation.

The Problem

// Player.h — DOES NOT compile alone

#pragma once

class Player {
 std::string name;  // ERROR: std::string not declared — need <string>

 HealthComponent* health; // ERROR: HealthComponent not declared

};
```

### The Fix

```cpp
// Player.h — compiles alone

#pragma once

#include <string>

class HealthComponent; // forward declaration — enough for a pointer

class Player {
 std::string name;
 HealthComponent* health; // forward-declared, pointer is fine

};
```

**Rule: Include what you use.** Don't rely on transitive includes (`A.h` includes `<string>`, so `B.h` that includes `A.h` appears to have `<string>`). Transitive includes are build-time accidents — they break when `A.h` removes its `<string>` dependency.

### Forward Declaration vs #include

| You Need... | Use | Because |
|-------------|-----|---------|
| Pointer/reference to type | `class Foo;` | Compiler only needs to know "Foo is a class" |
| Value member (`Foo m_foo;`) | `#include "Foo.h"` | Compiler needs sizeof(Foo) |
| Call method on object | `#include "Foo.h"` | Compiler needs the full declaration |
| Inherit from type | `#include "Foo.h"` | Compiler needs the full class definition |

[!tip] Include in `.cpp`, forward-declare in `.h`. This is the golden rule of fast builds.

## Pimpl — Pointer to Implementation

**Intent:** Hide implementation details behind an opaque pointer, eliminating compile-time dependencies on the implementation.

### The Problem

```cpp
// \u274c WITHOUT PIMPL: Every client of Player.h includes 50 headers transitively
#include "HealthComponent.h"
#include "InventoryComponent.h"
#include "SkillTreeComponent.h"
// ... 47 more ...

class Player {
public:
 void TakeDamage(float amount);
private:
 HealthComponent health;     // sizeof(HealthComponent) needed
 InventoryComponent inventory;
 SkillTreeComponent skills;
 // Adding a new component = ALL clients recompile
};
```

If `HealthComponent.h` changes, every .cpp that includes `Player.h` recompiles — even if they never call health-related methods.

### The Pattern

```cpp
// Player.h — MINIMAL includes
#pragma once
#include <memory>

class Player {
public:
 Player();
 ~Player(); // MUST be defined in .cpp (where Impl is complete)
 Player(Player&&) noexcept; // movable — declare in .h, define in .cpp
 Player& operator=(Player&&) noexcept;
 
 void TakeDamage(float amount);
 
private:
 struct Impl; // forward-declared nested struct
 std::unique_ptr<Impl> pImpl; // opaque pointer — sizeof(unique_ptr) = sizeof(pointer)
};

// Player.cpp — ALL implementation details live here
#include "HealthComponent.h"
#include "InventoryComponent.h"
#include "SkillTreeComponent.h"

struct Player::Impl {
 HealthComponent health;
 InventoryComponent inventory;
 SkillTreeComponent skills;
};

Player::Player() : pImpl(std::make_unique<Impl>()) {}
Player::~Player() = default; // must be AFTER Impl is complete (in .cpp)
Player::Player(Player&&) noexcept = default;

void Player::TakeDamage(float amount) {
 pImpl->health.ApplyDamage(amount); // delegation — one extra indirection
}
```

**What Changed:** `Player.h` now includes NOTHING but `<memory>`. Changing `HealthComponent.h` recompiles only `Player.cpp` — not the other 499 .cpp files that include `Player.h`.

### The Trade-offs

| Gain | Cost |
|------|------|
| Header deps drop to near-zero | One heap allocation per Pimpl object |
| ABI stability (change Impl, no relink) | One extra pointer indirection on every member access |
| Hide proprietary implementation | More boilerplate (Pimpl + delegation to Impl) |
| Move semantics work naturally | Can't inline Pimpl-delegated methods |

[!warning] Pimpl is NOT free. The heap allocation + pointer indirection + cascaded cache miss on first access are real costs. Use Pimpl for classes in hot headers (included by 50+ TUs), not for internal implementation details used in one .cpp.

### Pimpl Variants

**`shared_ptr` Pimpl — Fewer Rules:**

```cpp
// shared_ptr<Impl> does NOT require destructor definition in .cpp

class Player {
 struct Impl;
 std::shared_ptr<Impl> pImpl; // type-erased deleter — no incomplete-type rule

public:
 Player();
 // ~Player() = default; // WORKS in header! shared_ptr's deleter is type-erased

};
```

`shared_ptr` stores the deleter at construction time (type erasure in the control block), so the destructor doesn't need to see the complete `Impl` type. `unique_ptr` stores the deleter as part of its type — the compiler must instantiate `default_delete<Impl>` which requires `Impl` to be complete. Trade-off: `shared_ptr` adds atomic reference counting overhead (not needed for Pimpl — you never share it).

**In-Place Pimpl — No Heap Allocation:**

```cpp
// For small Impl objects (≤ 64 bytes), allocate inline to avoid heap overhead
class Player {
 struct Impl; // forward-declared, sizeof unknown in header
 static constexpr size_t ImplSize = 256; // hand-tuned upper bound
 alignas(std::max_align_t) char storage[ImplSize]; // raw storage, no heap
public:
 Player();
 ~Player();
 // placement new + explicit destructor call in .cpp
};

// Player.cpp
Player::Player()  { pImpl = new (storage) Impl(); }
Player::~Player() { reinterpret_cast<Impl*>(storage)->~Impl(); }
```

This avoids the heap allocation entirely — useful when `Player` is created/destroyed every frame. Cost: `sizeof(Player)` increases, manual lifetime management, and fragile (must update `ImplSize` when Impl grows).

**The Debugging Pain (Not in the Trade-Off Table):**

```cpp
// Debugger shows: pImpl = {unique_ptr} → 0x1a3f...
// You cannot expand members. You cannot see health, inventory, skills.
// You MUST step into the .cpp file to inspect Impl state.
```

This is the #1 complaint about Pimpl in production. Mitigations: (1) Add `DisplayDebug()` methods that dump Impl state to a string; (2) Use Natvis (.natvis files in Visual Studio) to teach the debugger how to expand your Pimpl types; (3) Accept that Pimpl is a build-time optimization that trades development-time visibility.

## Argument-Dependent Lookup (ADL)

ADL is the reason `std::cout << "hello"` finds `operator<<` without you writing `std::operator<<`. It's powerful and subtle — and the source of hard-to-debug surprises.

### How ADL Works

When you call `foo(x)`, the compiler searches for `foo` in:
1. The current namespace (and its parents)
2. The namespaces of the ARGUMENTS' types (and their parents)

```cpp
namespace Audio {
 struct Sound {};
 void Play(Sound s) { /* ... */ } // found via ADL
}

Audio::Sound boom;
Play(boom); // ADL finds Audio::Play — no "Audio::" needed
```

### The Trap — ADL Hijacking

```cpp
// \u274c TRAP: ADL picks up an unintended overload
namespace Library {
 struct Vec3 { float x, y, z; };
}

namespace MyGame {
 void normalize(Library::Vec3& v) { /* my implementation */ }
}

MyGame::normalize(vec); // Calls MyGame::normalize — fine

// LATER: Library adds its own normalize:
namespace Library {
 void normalize(Vec3& v) { /* library's implementation */ }
}

normalize(vec); // NOW AMBIGUOUS — ADL finds BOTH!

```

**Mitigation:** Use qualified calls for important functions. Instead of `swap(a, b)`, write `using std::swap; swap(a, b)` — which prefers ADL-found `swap` but falls back to `std::swap`.

### The Swap Two-Step — ADL's Most Important Idiom

```cpp
template<typename T>
void MyAlgorithm(std::vector<T>& items) {
 // \\u274c WRONG: Hardcodes std::swap — misses user-provided specializations

 std::swap(items[i], items[j]);
 
 // \\u2705 CORRECT: Two-step — prefers ADL swap, falls back to std::swap

 using std::swap;
 swap(items[i], items[j]); // unqualified call triggers ADL

}
```

Here's WHY this matters. A user writes `FastSwap` for their type:

```cpp
namespace Game {
 struct BigMatrix {
     // Heavy data — copying is expensive
     void swap(BigMatrix& other) noexcept { /* pointer swap, O(1) */ }
 };
 // Custom swap found via ADL:
 void swap(BigMatrix& a, BigMatrix& b) noexcept { a.swap(b); }
}
```

If `MyAlgorithm` calls `std::swap`, it copies BigMatrix elements — O(n). If `MyAlgorithm` uses the two-step (`using std::swap; swap(...)`), ADL finds `Game::swap()`, which pointer-swaps — O(1). The two-step means: "use the best swap available for this type, and std::swap if nothing else exists."

### Hidden Friend — ADL-Only Functions

```cpp
namespace Game {
 class Vec3 {
     float x, y, z;
 public:
     // Hidden friend: defined inline in class body, found ONLY via ADL
     friend Vec3 operator+(const Vec3& a, const Vec3& b) {
         return {a.x + b.x, a.y + b.y, a.z + b.z};
     }
     friend bool operator==(const Vec3& a, const Vec3& b) = default;
 };
 // operator+(Vec3, Vec3) is NOT in the enclosing namespace scope
 // It is ONLY visible to ADL. Not found by unqualified lookup in Game::
}

Game::Vec3 a, b;
auto c = a + b;    // OK — ADL finds hidden friend
// auto d = Game::operator+(a, b); // ERROR — not in Game namespace scope!
```

Hidden friends reduce overload set pollution. The compiler only considers them when the arguments involve your type — exactly when you want them considered. This is the recommended pattern for operator overloads in C++20.

### ADL and `using namespace`

```cpp
// \u26a0\ufe0f NEVER write this in a header:
using namespace std; // poisons every TU that includes this header

// \u2705 In .cpp files only — and even then, prefer specific using-declarations:
using std::string;
using std::vector;
```

## The One Definition Rule (ODR)

Every entity in your program must have exactly ONE definition across all translation units.

### What's Allowed Multiple Times

  • **Declarations** (function prototypes, `extern` variables, forward class declarations)


  • **Inline functions** and **constexpr variables** (compiler copies into each TU)


  • **Templates** (instantiated on demand — compiler deduplicates)


  • **Class definitions** (appear in every TU that uses the class — must be token-identical)


### The Trap — ODR Violation via Inconsistent Headers

```cpp
// config.h in TU #1:

#define DEBUG_MODE 1

#include "MyClass.h" // MyClass uses #ifdef DEBUG_MODE internally

// config.h in TU #2:

#define DEBUG_MODE 0

#include "MyClass.h" // DIFFERENT definition of MyClass — ODR VIOLATION

```

**Result:** Undefined behavior. Linker may or may not catch it. Symptoms: one TU calls debug version of a method, another calls release version — heap corruption, mystery crashes.

### What an ODR Violation Actually Looks Like

When the linker DETECTS the mismatch (it often can't), you get an error like:

```
// GCC/Clang:
ld: error: duplicate symbol: MyClass::debugField
>> defined in tu1.o
>> defined in tu2.o

// MSVC:
error LNK2005: "int MyClass::debugField" already defined in tu1.obj
```

When the linker DOESN'T detect it (different inline function bodies in different TUs), there's no error at all. The linker picks one definition arbitrarily. You have two TUs with different behavior — and no diagnostic:

```cpp
// Version A (TU #1): inline int size() { return 10; }
// Version B (TU #2): inline int size() { return 20; }
// Linker picks one. Which one? Unspecified. Behavior changes per build.
```

**The ODR in Practice — A Daily Trap:**

```cpp
// \\u274c TRAP: Different inline function definitions via different #includes
// Entity.h (library v1.0)
inline int GetMaxEntities() { return 100; }

// Entity.h (library v1.1 — upgraded silently)
inline int GetMaxEntities() { return 200; }

// TU #1 compiled with v1.0 header, TU #2 with v1.1 header
// Link succeeds. Program behavior: random.
```

**Only fix:** Rebuild EVERYTHING when any header changes. Or use C++20 modules, where the module interface is compiled once and imported — the definition is guaranteed identical across all importing TUs.

### ODR and Modules (C++20)

C++20 modules eliminate ODR concerns from macros and header ordering:

```cpp
// MyModule.ixx — compiled ONCE, imported everywhere
export module MyModule;
// No preprocessor state leaks. Same definition in every importing TU. Guaranteed.
```

## Dependency Inversion in Build Structure

Coupling physical (build) dependencies to logical dependencies:

```
// BAD: Logical dependency graph = physical dependency graph
Application -> Engine -> Renderer -> OpenGL
// Changing OpenGL header = Application recompiles. Every link in chain recompiles.

// GOOD: DIP applied to build structure
Application -> IEngine (abstract interface)
Engine -> IRenderer (abstract interface)
Renderer -> OpenGL (implementation, not visible upward)
// Changing OpenGL header = only Renderer.cpp recompiles.
```

This is why UE5 splits every module into `Public/` (interfaces, abstract classes) and `Private/` (implementations). The Build.cs file declares the dependency graph, and UBT ensures implementation headers never leak upward.

## Two-Way Explanation

**Beginner:** Every `#include` copies a whole file into your code. Include fewer things = faster builds. Forward-declare classes when you only need a pointer. Pimpl hides everything behind a pointer so your header stays tiny. Don't write `using namespace` in headers — it leaks into everyone else's code. Self-sufficient headers mean every `.h` includes everything it needs, no relying on accidental transitive includes.

**Experienced:** Build-time dependency management is mechanical sympathy for the compiler. The critical path is: (1) forward-declare in headers, include in .cpp — reduces the transitive dependency closure; (2) Pimpl eliminates ALL implementation dependencies from the header's TU at the cost of one heap allocation and pointer indirection; (3) ADL-aware API design prevents silent overload changes when upstream libraries add functions; (4) C++20 modules replace textual inclusion with a pre-compiled module interface — the ODR guarantee without macro leakage. The build graph should mirror the dependency inversion graph: high-level modules depend on abstract interfaces, not concrete implementations.
